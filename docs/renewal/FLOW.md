# コンテンツ移行の全体の流れ(リニューアル後)

ディレクターが、案件の始まりから移行後のチェックまでに何をするかを、リニューアル後の形で書いた。
リニューアルの設計書は、この流れを前提にする。

## この文書の元

- ユーザーから共有された社内資料「0-1:全体の流れ(一時完成)」(2026-10-05 時点、未完成)を元にした。資料の工程番号(1-1〜6-2)をそのまま使う。
- 資料ではチームごとに担当を分けているが、この文書では、自治体と移行業者と開発チーム以外の作業をまとめて「ディレクター」の作業として書く(2026-10-05 ユーザー)。
- 社内のスプレッドシートの URL など、公開リポジトリに置けない情報は載せていない。

## 登場する人

| 呼び方 | 役割 |
| --- | --- |
| ディレクター | 案件を進める人。移行管理シートを作り、ルールとマニュアルを用意し、確認画面(校正台)で直した HTML を確定し、取り込みと移行後のチェックを行う。案件ごとに1人、確認画面での確認に使えるのは1日5時間 |
| 自治体 | 顧客。ページの一覧を出し、移行の要不要、カテゴリ、ルールとマニュアルを確かめる。個別のページの質問に答える |
| 移行業者 | CMS の管理画面で、取り込んだページの仕上げ(カテゴリ、ファイル、公開の設定など)を行う |
| 開発チーム | いまと同じく、CMS のコンテンツ移行の環境を用意し、取り込みの不具合に対応する。この仕組みのための CMS の変更は頼めない |

## 変わるところ

いまは、旧サイトのページをそのまま CMS に取り込み、移行業者が CMS の管理画面でアクセシビリティの手直しをしている。
リニューアル後は、取り込む前にディレクターが確認画面で直しを確定し、直した HTML を CMS に取り込ませる。
手直しの多くが移行業者の作業から前の工程へ移るので、取り込み後の移行業者と承認の工程が短くなる。

| 工程 | いま | リニューアル後 |
| --- | --- | --- |
| 1 計画・方針・JIS 試験 | 変わらない | 1-1 で、本文を AI(さくらか Gemini)に送ることの同意を確かめる。1-2 で決めた対応の水準を、6-2 の受け入れの確認(miChecker)の基準にも使う |
| 2 移行管理シート | 変わらない | 変わらない。シートが固まったら(2-6)、一括処理の入力にする |
| 3 ルール・マニュアル | 移行業者が読む文書 | 文書に加えて、自治体ごとの決まりを一括処理の「案件の設定」に入れる(3-4) |
| 4 取込・準備 | 旧サイトのページを取り込む | 取り込みテストに「CMS 取込試験」と「一括処理の試走」を加える。取込回ごとに、一括処理、確認画面での確定、FTP への配置を挟み、FTP 上の直した HTML を取り込む |
| 5 その他 | 変わらない | 禁則文字と強制アクセシビリティチェックの決まりを、一括処理の変換の決まりと揃える |
| 6 移行作業 | 移行業者が手直しと仕上げを行う | 移行業者は仕上げが中心になる。移行後のチェックで、手直しの残りと miChecker の結果を見る |

## 全体の流れ

工程の番号は元の資料のもの。★はリニューアルで加わる工程、☆は中身が変わる工程。

```
1 計画・方針・JIS 試験                 ディレクター
   1-1 移行計画書 ☆(AI への送信の同意) → 1-2 JIS 実装計画
   → 1-3 アクセシビリティ方針 → 1-4 JIS 試験
        │
2 移行管理シート                        自治体 ⇄ ディレクター
   2-1 ページ一覧 → 2-2 シート作成 → 2-3 要不要の精査
        │                     │
        │                     └→ 4-1 取り込みテスト ☆(2-3 が済んでから)
        │                          ★ CMS 取込試験、★ 一括処理の試走(1回目)
        │                              │
   2-4 カテゴライズ → 2-5 確認           3 ルール・マニュアル ☆(4-1 の結果を見て)
   → 2-6 シートが固まる                  3-1 ベース作成 → 3-2 自治体の確認 → 3-3 完成
        │                              ★ 3-4 案件の設定に自治体ごとの決まりを入れる
        │                              ★ 一括処理の試走(2回目)で取込回の大きさを決める
        └──────────────┬───────────────┘
                       │
   ┌─ 取込回ごとに繰り返す ───────────────────────────────────┐
   │ ★ 4-5 一括処理(旧ページの取得、本文の抽出、候補、確認の深さ)    │
   │ ★ 4-6 確認画面(校正台)で確定                                 │
   │ ★ 4-7 共有ドライブへの書き出し、FTP への配置、移行元 URL の置き換え │
   │ ☆ 4-3 取り込み作業(指定の取り込み日に、FTP 上の直した HTML を)  │
   │      ※ 4-3 だけは、4-2 準備作業(5 その他の完了)を待つ          │
   │ 4-4 移行業者への連絡(初回はシート、ルール、マニュアルを共有)      │
   │ ☆ 6-1 移行作業(移行業者。仕上げが中心)                         │
   │ ☆ 6-2 移行後チェック(手直しの残り、miChecker)                   │
   └─────────────────────────────────────────┘

5 その他(順不同、4-2 までに)            ディレクター(開発チーム)
   5-1 環境構築 / 5-2 グループ・署名 / 5-3 メールフォーム
   / 5-4 禁則文字 ☆ / 5-5 注意事項の共有
```

4-5〜4-7(一括処理、確定、書き出し)は CMS の環境に頼らないので、3-4 と2回目の試走が済めば、4-2 と 5 その他の完了を待たずに始められる。
CMS に取り込む 4-3 だけが、4-2(5-1〜5-5 の完了)を待つ。

## 工程ごとの説明

変わらない工程は短く、変わる工程と加わる工程は詳しく書く。

### 1 計画・方針・JIS 試験

1-1〜1-4 は変わらない。

- 1-1 の移行計画書で、本文を AI(さくらか Gemini)に送って修正の候補を作ることについて、自治体の同意を確かめる(同意は営業が案件ごとに取る)。同意が取れない案件の扱いは決まっていない。
- 1-2 の JIS 実装計画で決めた対応の水準は、6-2 の受け入れの確認(miChecker)で、どの指摘を残してよいかの基準にする。

### 2 移行管理シート

2-1〜2-6 は変わらない。

- 2-3 が済んだら、4-1 の取り込みテストを始められる(元の資料の決まり)。
- 2-6 でシートが固まったら、「移行する」ページの一覧を一括処理の入力にする。ページ数を数えるときは、シートの行数ではなく「移行する」の数を使う(遠野市のシートでは 5,628 行のうち 1,922 ページ)。
- 一括処理と確認画面は、シートに「AI 修正」のタブを足して、そこに書き込む。既存の「一覧」には書き込まない。「一覧」の列(証跡、移行完了日など)へディレクターが写すかどうかは決まっていない。
- 元の資料のとおり、シートは上書きせず、変更したら版を上げる。版が上がったときに「AI 修正」のタブと書き戻し先をどう引き継ぐか、取込回の途中で新しい版が返ってきたときにどの版を一括処理の入力にするかは、決まっていない。
- 移行が始まったあとに追加や更新があったページ(差分)は、元の資料のとおり 2-1〜2-6 を繰り返し、「差分の取込回」として下の取込回の輪に載せる。

### 3 ルール・マニュアル

元の資料のとおり、3-1 のベース作成は、4-1 の取り込みテストの結果と、返却されたシートを見て行う。
3-2、3-3 は変わらない。

★ 3-4 として、ルールとマニュアルのうち、自治体ごとに決めた表記や扱いを、一括処理の「案件の設定」に入れる。
たとえば、日付や電話番号の書き方、画像の代替テキストの方針、ページ内リンクの扱い(CMS に取り込むと `#id` のアンカーは残らないので、共通のルール「ページ内アンカーリンク」に沿って、該当箇所を文章で示す形に直す)。
共通のルール(アクセシビリティの移行ルール)は案件をまたいで使い、案件の設定はその上に重ねる。
確認画面で「このルールを案件の全ページで採用」を押した決定も、案件の設定に入る。
案件の設定の変更は、まだ確定していないページにだけ効く。
取り込み済みのページには遡らないので、6-2 で数え、必要なら移行業者の手直しか取り込み直しに回す。
自治体の方針に関わる決定は、確認画面で決めず、3-2 と同じく自治体に確かめる。

3-4 のあとに、一括処理の試走(2回目)を行い、取込回の大きさと日程を決める(下の「日程の目安」)。

### 4 取込・準備

**4-1 取り込みテスト** ☆(2-3 が済んでから。3-1 の前)
いまの取り込みテスト(実際の移行対象ページをランダムに取り込み、ページの傾向を確かめる)に、次の2つを加える。

- ★ **CMS 取込試験**: 案件の取込環境で、CMS が受け付けるタグと属性を確かめる(`docs/cms-import-tag-test/`)。初めての環境のときと、CMS の取込の仕組みが変わったときに行う。
- ★ **一括処理の試走(1回目)**: 移行対象からページを抜き出して一括処理にかけ、取得できないページ、本文の抽出の当たり外れ、候補の傾向を見る。結果は 3-1 のルールとマニュアル、3-4 の案件の設定の材料にする。

CMS は一度取得した HTML を同じ移行管理 ID では取得し直さないので、取り込みテストと本番とで、取込環境か移行管理 ID を分ける。

**4-2 準備作業**
変わらない。5 その他(5-1〜5-5)の完了を待つ。
4-2 を待つのは 4-3 の取り込みだけで、4-5〜4-7 は先に進めてよい。

**★ 4-5 一括処理**(取込回ごと)
ディレクターの PC で、Claude Code に一括処理を動かしてもらう(Claude Code は道具を動かす係で、修正の候補を作る AI はさくらか Gemini)。
一括処理は、その取込回の「移行する」ページについて、次を行う。

1. 旧サイトのページを取得し、本文を抜き出す。
2. 共通のルールと案件の設定から、修正の候補を作る。
3. 安全な候補だけを自動で採用する。
4. 直したあとの HTML に残る指摘を数える(miChecker と同じ検査)。
5. ページごとに確認の深さを決め、結果を共有ドライブに書き出す。

あわせて、取り込みで失敗する条件を前もって調べ、シートの「AI 修正」タブに理由を書く。

- 取得できなかったページ(404、エラーのページなど)。元の資料の注意と同じく、旧サイトから取得するページは 100% 取れる保証がないことを、自治体に前もって伝えておく。
- 登録できないページ(ページタイトルが60字以上、グループが空欄)。
- 取り込みを失敗させる参照(存在しないファイルや画像、SVG の画像ファイルなど)。

**★ 4-6 確認画面(校正台)で確定**(取込回ごと)
ディレクターが、待ち行列のページを1枚ずつ確認して確定する。

- しっかり確認のページは、修正前と修正後を読んで判断する。
- さっと確認のページは、差分を見て採用する。
- 確認不要のページは開かない。
- 判断に迷う指示は後回しにし、質問の下書きを付ける。後回しの指示が残るページは、その取込回の書き出し(4-7)から外し、回答が来たあとの取込回に入れる。
- 同じ決まりが案件の多くのページに出てくるときは、「このルールを案件の全ページで採用」で一度に決める。

**★ 4-7 書き出し、FTP への配置、移行元 URL の置き換え**(取込回ごと)

1. 確定したページの HTML が、共有ドライブの案件のフォルダに書き出される(名前は移行管理 ID)。
2. ディレクターが、取込回のフォルダの中身を、FTP 領域の案件のフォルダに上げる。FTP 上の URL は移行管理 ID だけで決まり、取込回で分けない。CMS は取り込みの最初の段階で HTML を取得し、同じ移行管理 ID では取得し直さないので、上げるのは確定したページだけにする。
3. 旧 URL と FTP 上の URL の対応表をもとに、取込データの「移行元 URL」を FTP 上の URL に置き換える(GAS で行う)。

置き換えるのは、取込データとして出す「移行元 URL」だけにする。
「一覧」と「AI 修正」のタブには旧 URL を残す。
移行業者がシートを旧 URL で探したり、取込データと移行元の差を旧サイトで確かめたりするため。
旧 URL と新しいページの対応(リダイレクトの元)も、シートで持つ。

**4-3 取り込み作業** ☆(取込回ごと)
元の資料のとおり、取り込み日は指定される。
取込回の数と日程は、取れる取り込み日の枠に合わせて決める。
CMS は、FTP 上の直した HTML を取り込む。
画像と PDF は旧サイトの絶対 URL のままで取り込まれる(2026-10-05 に確認)。CMS は移行元 URL と同じサーバの画像とファイルだけを素材にするので、FTP に写して素材にする案もある(`ARCHITECTURE.md` の「CMS に渡す HTML の約束」)。
取り込みは、担当者が CMS の画面のボタンで始める(日時を指定して自動で動く仕組みは無い)。
取り込みのあとに、内部リンクに変えるボタンを押す。後の取込回のページへのリンクは、そのページを取り込んだあとにもう一度押すと変わる。
取り込みでエラーになったページは、いまと同じく、移行の開始に影響がない量なら後日の対応にする。
原因が直した HTML にあれば、一括処理の出力を直して次の取込回に入れる。
原因が旧ページそのものにあれば、いまと同じく移行業者が手で登録する。

**4-4 移行業者への連絡**
初回は、いまと同じく、シート、ルール、マニュアルを共有する。
直した HTML が取り込まれていること、手直しが要らなくなった項目を、マニュアルに書く。
2回目からは、取込回ごとに「取り込んだページの範囲」を知らせる。

### 5 その他

5-1〜5-5 は変わらない。

- 5-2 の署名には、CMS の強制アクセシビリティチェック(公開を止める文字。例: TEL、FAX)に当たる文字が残っていることがある。本文も同じで、残ると移行業者がページを公開できず、6-1 が延びる。強制アクセシビリティチェックの決まりを、一括処理の案件の設定に入れておく。
- 5-4 の禁則文字の登録は、いまも「マニュアルの変換の決まりと禁則文字の変換の決まりが違う」ことが多い。リニューアル後は、一括処理の変換の決まりも加わるので、3つ(マニュアル、禁則文字、案件の設定)を同じ内容に揃える。

### 6 移行作業

**6-1 移行作業** ☆(移行業者、取込回ごと)
4-4 の初回の連絡と 5-5 が済み、取込回1が取り込まれたら始める。
アクセシビリティの手直しは、ディレクターが取り込む前に済ませている。
移行業者の作業は、CMS の管理画面での仕上げが中心になる(カテゴリ、ファイル、画像の並び、公開の設定など)。
個別のページの質問は、いまと同じくディレクターに送る。

**6-2 移行後チェック** ☆(ディレクター、取込回ごと)
いまのチェック(移行ページ数の認識合わせ、内容の不備、編集中のステータス、内部リンクが外部リンクのまま残っていないか、ランダムの目視)に、次を加える。

- 移行業者がさらに手直しした箇所を数える。数が多いルールは、共通のルールか案件の設定を見直す。
- 公開ページに FTP のサーバへのリンクが残っていないかを確かめる。
- 取り込んだページを取り直し、旧ページ、確定した HTML、取り込んだあとのページの3つを比べる(本文の差、画像と PDF が素材になったか、内部リンクに変わったか。`ARCHITECTURE.md` の「取り込み後の比べ合わせ」)。
- CMS のプレビューを miChecker で検査し、本文に起因する指摘が残っていないかを確かめる(`goal2-app/public/michecker-compare.html` で前後を比べる)。基準は 1-2 で決めた対応の水準。

## 取込回の回し方

取込回は、確認画面での確定から移行後チェックまでを、小さな単位で回すためのもの。
1回目の取込回で、2回目以降の大きさと日程を決め直す。
次の表は、取り込み日が週に1回取れる場合の例。

| 取込回 | ディレクター | 移行業者 |
| --- | --- | --- |
| 1 | 一括処理と確定、FTP、取り込み | (待ち) |
| 2 | 一括処理と確定、FTP、取り込み。取込回1の移行後チェック | 取込回1の移行作業 |
| 3 | 一括処理と確定、FTP、取り込み。取込回2の移行後チェック | 取込回2の移行作業 |
| … | … | … |
| 最後 | 回答待ちだったページだけの取込回 | 一つ前の取込回の移行作業 |

- 質問の回答待ちのページは、回答が来たあとの取込回に入れる。最後に、回答待ちだったページだけの取込回を1回取っておく。
- 最後の取込回までに回答が来ないページの扱い(いまと同じく取り込み、質問を移行業者経由で残すか)は、決まっていない。

## 日程の目安

移行作業の期間はおよそ3か月(約60営業日)。
このうち、確認画面での確定に使えるのは、4-1 の試走と 3-4 のあとの試走の期間と、最後の取込回の取り込み、6-1、6-2 の期間(合わせて2週ほど)を除いた、およそ50営業日とみる。
1日5時間は確認画面での確認だけの時間で、6-2、質問への対応、FTP の作業はこれに含めない(含めるかどうかは決まっていない)。

| 移行するページ数 | 1日に確定するページ数 | 1ページの平均時間 |
| --- | --- | --- |
| 1,000 | 20 | 約15分 |
| 3,000 | 60 | 約5分 |
| 10,000 | 200 | 約1.5分 |

10,000 ページの案件は、確認不要のページを開かずに済ませ、さっと確認のページを1分以内で流せることが前提になる。
仮に確認不要が40%、さっと確認が45%(1分)、しっかり確認が15%(10分)とすると、10,000 ページで約325時間(さっと確認 75 時間、しっかり確認 250 時間)、1日5時間で65日かかり、50日に収まらない。
この割合は推測なので、一括処理の試走で実際の割合と時間を測る。

収まらないときの打ち手は、効く順に次のとおり。

1. しっかり確認の数と時間を減らす。時間の大半(上の例で約77%)を占めるので、表と見出しの候補の精度を上げる、しっかり確認のページで読む範囲を指示の箇所に絞る。
2. 確定を早く始める。4-5〜4-7 は 4-2 を待たないので、3-4 と2回目の試走が済んだらすぐ始める。
3. 確認不要の割合を上げる。案件の設定で安全に自動で採用できる決まりを増やす。ただし、さっと確認(1分)から確認不要に10ポイント移しても約17時間しか減らない。

ディレクター1人という前提を崩す打ち手(しっかり確認のページだけ別の人が確認する、など)は、ここでは扱わない。

## データの置き場所

| 置き場所 | 置くもの | 誰が書くか |
| --- | --- | --- |
| 移行管理シート | ページの一覧、移行の要不要、カテゴリ、質問と回答、取込データ。「AI 修正」タブに確認の状態、件数、取り込めない理由、証跡の場所、FTP 上の URL、旧 URL | ディレクター、自治体、一括処理と確認画面(GAS 経由。「AI 修正」タブだけ) |
| 共有ドライブ | 案件のフォルダ。ページごとの候補と判断(証跡)、直した HTML、案件の設定、取込回ごとの書き出し | 一括処理と確認画面 |
| FTP 領域 | 案件のフォルダ(移行管理 ID の名前の直した HTML。取込回で分けない) | ディレクター |
| CMS | 取り込んだページ | 取り込み(CMS)、移行業者 |
| 共通のルール | アクセシビリティの移行ルール(`a11y-migration-kb/`) | この仕組みを整える人(案件をまたいで繰り返し出る決まりを足す) |

## 決まっていないこと、確かめること

- 取込回ごとの取り込み日を誰が指定し、案件の期間中に何回取れるか。CMS 取込試験の取り込みはユーザー自身が行えたので、取込環境では自分で動かせる可能性もある。
- 「AI 修正」タブの列と、既存の「一覧」の列(証跡、移行完了日など)へ写すかどうか。
- シートの版が上がったとき、「AI 修正」タブと書き戻し先をどう引き継ぐか。
- 差分(追加や更新があったページ)を、差分の取込回としてどう回すか。
- 共有ドライブの案件のフォルダの形(`ARCHITECTURE.md` に案がある)。
- 移行業者に、直した HTML が取り込まれていることと、手直しが要らなくなった項目をどう伝えるか(マニュアルの書き換えを含む)。
- 質問を書く欄。ディレクターから自治体への質問を、移行業者から SV への質問欄(質問欄(1)〜(3))と同じ欄に書くと、6-1 の運用と混ざる。「AI 修正」タブに書くか、別の欄を設けるか。
- 最後の取込回までに回答が来ないページの扱い。
- 案件の設定の変更や回答で決まりが変わったとき、取り込み済みのページをどうするか(6-2 で数えたあと、移行業者の手直しか取り込み直しか)。
- 取り込みエラーのページを取り込み直す回し方と、「移行の開始に影響がない量」の基準。
- 旧サイトの公開が終わる日と、最後の取込回と 6-1 の完了の関係。画像と PDF は旧サイトの URL から取り込まれるので、旧サイトが先に閉じると成り立たない。一括処理が取得した旧ページと画像、PDF を共有ドライブに保存しておくか。
- CMS の強制アクセシビリティチェックと禁則文字の一覧を、案件の設定にどう写すか。
- 1日5時間に、6-2、質問への対応、FTP の作業を含めるか。
- 本文を AI に送ることの同意が取れない案件で、4-5 をどうするか。
- CMS が受け付けるタグと属性の細部(4-1 の CMS 取込試験の結果待ち)。取り込みの振る舞いを調べた結果は `ARCHITECTURE.md` の「CMS に渡す HTML の約束」にある。
- 画像と PDF を旧サイトの URL のままにするか、FTP に写して CMS の素材にするか。
