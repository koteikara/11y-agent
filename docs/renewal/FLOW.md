# コンテンツ移行の全体の流れ(リニューアル後)

ディレクターが、案件の始まりから移行後のチェックまでに何をするかを、リニューアル後の形で書いた。
リニューアルの設計書は、この流れを前提にする。

## この文書の元

- ユーザーから共有された社内資料「0-1:全体の流れ(一時完成)」(2026-10-05 時点、未完成)を元にした。資料の工程番号(1-1〜6-2)をそのまま使う。
- 資料ではチームごとに担当を分けているが、この文書では、自治体と移行業者と開発チーム以外の作業をまとめて「ディレクター」の作業として書く(2026-10-05 ユーザー)。
- 社内のスプレッドシートの URL など、公開リポジトリに置けない情報は載せていない。

## 登場する人

| 呼び方 | 役割 |
| --- | --- |
| ディレクター | 案件を進める人。移行管理シートを作り、ルールとマニュアルを用意し、確認画面(校正台)で直した HTML を確定し、取り込みと移行後のチェックを行う。案件ごとに1人、確認に使えるのは1日5時間 |
| 自治体 | 顧客。ページの一覧を出し、移行の要不要、カテゴリ、ルールとマニュアルを確かめる。個別のページの質問に答える |
| 移行業者 | CMS の管理画面で、取り込んだページの仕上げ(カテゴリ、ファイル、公開の設定など)を行う |
| 開発チーム | CMS のコンテンツ移行の環境を用意し、取り込みの不具合に対応する |

## 変わるところ

いまは、旧サイトのページをそのまま CMS に取り込み、移行業者が CMS の管理画面でアクセシビリティの手直しをしている。
リニューアル後は、取り込む前にディレクターが確認画面で直しを確定し、直した HTML を CMS に取り込ませる。
手直しの多くが移行業者の作業から前の工程へ移るので、取り込み後の移行業者と承認の工程が短くなる。

| 工程 | いま | リニューアル後 |
| --- | --- | --- |
| 1 計画・方針・JIS 試験 | 変わらない | 変わらない。JIS 試験の結果は、取り込み後の受け入れの確認(miChecker)の基準にも使う |
| 2 移行管理シート | 変わらない | 変わらない。シートが固まったら(2-6)、一括処理の入力にする |
| 3 ルール・マニュアル | 移行業者が読む文書 | 文書に加えて、自治体ごとの決まりを一括処理の「案件の設定」に入れる |
| 4 取込・準備 | 旧サイトのページを取り込む | 取り込みテストに「CMS 取込試験」を加える。取込回ごとに、一括処理、確認画面での確定、FTP への配置を挟み、FTP 上の直した HTML を取り込む |
| 5 その他 | 変わらない | 禁則文字の登録を、一括処理の変換の決まりと揃える |
| 6 移行作業 | 移行業者が手直しと仕上げを行う | 移行業者は仕上げが中心になる。移行後のチェックで、手直しの残りと miChecker の結果を見る |

## 全体の流れ

工程の番号は元の資料のもの。★はリニューアルで加わる工程、☆は中身が変わる工程。

```
1 計画・方針・JIS 試験          ディレクター
   1-1 移行計画書 → 1-2 JIS 実装計画 → 1-3 アクセシビリティ方針 → 1-4 JIS 試験
        │
2 移行管理シート                 自治体 ⇄ ディレクター
   2-1 ページ一覧 → 2-2 シート作成 → 2-3 要不要の精査 → 2-4 カテゴライズ
   → 2-5 カテゴライズの確認 → 2-6 シートが固まる
        │
3 ルール・マニュアル ☆           ディレクター ⇄ 自治体
   3-1 ベース作成 → 3-2 自治体の確認 → 3-3 完成
   ★ 3-4 案件の設定に自治体ごとの決まりを入れる
        │
4 取込・準備 ☆                  ディレクター(開発チーム)
   4-1 取り込みテスト ☆(★ CMS 取込試験、★ 一括処理の試走)
   4-2 準備作業(5 その他 の完了を待つ)
        │
   ┌─ 取込回ごとに繰り返す ─────────────────────────┐
   │ ★ 4-5 一括処理(旧ページの取得、本文の抽出、候補、確認の深さ) │
   │ ★ 4-6 確認画面(校正台)で確定                              │
   │ ★ 4-7 共有ドライブへの書き出し、FTP への配置、移行元 URL の置き換え │
   │ ☆ 4-3 取り込み作業(FTP 上の直した HTML を取り込む)          │
   │ 4-4 移行業者への連絡(初回のみ。2回目からは取込回の知らせ)     │
   │ ☆ 6-1 移行作業(移行業者。仕上げが中心)                      │
   │ ☆ 6-2 移行後チェック(手直しの残り、miChecker)                │
   └──────────────────────────────────────┘
        │
5 その他(順不同、4-2 までに)     ディレクター(開発チーム)
   5-1 環境構築 / 5-2 グループ・署名 / 5-3 メールフォーム / 5-4 禁則文字 ☆ / 5-5 注意事項の共有
```

## 工程ごとの説明

変わらない工程は短く、変わる工程と加わる工程は詳しく書く。

### 1 計画・方針・JIS 試験

1-1〜1-4 は変わらない。
1-2 の JIS 実装計画で決めた対応の水準は、取り込み後の受け入れの確認(6-2 の miChecker)で、どの指摘を残してよいかの基準になる。

### 2 移行管理シート

2-1〜2-6 は変わらない。
2-6 でシートが固まったら、「移行する」ページの一覧を一括処理の入力にする。
シートには、一括処理と確認画面が書き込むための「AI 修正」のタブを足す(既存の「一覧」には書き込まない)。
ページ数を数えるときは、シートの行数ではなく「移行する」の数を使う(遠野市では 5,628 行のうち 1,922 ページ)。

### 3 ルール・マニュアル

3-1〜3-3 は変わらない。
★ 3-4 として、ルールとマニュアルのうち、自治体ごとに決めた表記や扱い(日付や電話番号の書き方、ページ内リンクの扱い、画像の代替テキストの方針など)を、一括処理の「案件の設定」に入れる。
共通のルール(アクセシビリティの移行ルール)は案件をまたいで使い、案件の設定はその上に重ねる。
確認画面で「このルールを案件の全ページで採用」を押した決定も、案件の設定に入る。

### 4 取込・準備

**4-1 取り込みテスト** ☆
いまの取り込みテスト(実際の移行対象ページをランダムに取り込み、ページの傾向を確かめる)に、次の2つを加える。

- ★ **CMS 取込試験**: 案件の取込環境で、CMS が受け付けるタグと属性を確かめる(`docs/cms-import-tag-test/`)。初めての環境のときと、CMS の取込の仕組みが変わったときに行う。
- ★ **一括処理の試走**: 移行対象からページを抜き出して一括処理にかけ、確認の深さ(しっかり確認、さっと確認、確認不要)の割合と、1ページの確認にかかる時間を測る。この数字で、取込回の大きさと日程を決める(下の「日程の目安」)。

**4-2 準備作業**
変わらない。5 その他(5-1〜5-5)の完了を待つ。

**★ 4-5 一括処理**(取込回ごと)
ディレクターの PC で、Claude Code に一括処理を動かしてもらう(Claude Code は道具を動かす係で、修正の候補を作る AI はさくらか Gemini)。
一括処理は、その取込回の「移行する」ページについて、次を行う。

1. 旧サイトのページを取得し、本文を抜き出す。
2. 共通のルールと案件の設定から、修正の候補を作る。
3. 安全な候補だけを自動で採用する。
4. 直したあとの HTML に残る指摘を数える(miChecker と同じ検査)。
5. ページごとに確認の深さを決め、結果を共有ドライブに書き出す。

取得できなかったページ(404、エラーのページなど)は、シートの「AI 修正」タブに理由を書き、確認画面では別に並べる。

**★ 4-6 確認画面(校正台)で確定**(取込回ごと)
ディレクターが、待ち行列のページを1枚ずつ確認して確定する。

- しっかり確認のページは、修正前と修正後を読んで判断する。
- さっと確認のページは、差分を見て採用する。
- 確認不要のページは開かない。
- 判断に迷う指示は後回しにし、質問の下書きを付ける。確定すると、シートの質問欄に下書きを書く。自治体の回答が来たら、そのページを開き直して判断する。
- 同じ決まりが案件の多くのページに出てくるときは、「このルールを案件の全ページで採用」で一度に決める。

**★ 4-7 書き出し、FTP への配置、移行元 URL の置き換え**(取込回ごと)

1. 確定したページの HTML が、共有ドライブの案件のフォルダに書き出される(名前は移行管理 ID)。
2. ディレクターが、取込回のフォルダを FTP 領域に上げる。
3. 旧 URL と FTP 上の URL の対応表をもとに、シートの取込データの「移行元 URL」を FTP 上の URL に置き換える(GAS で行う)。

**4-3 取り込み作業** ☆(取込回ごと)
置き換えた取込データで取り込む。
CMS は、FTP 上の直した HTML を取り込む。
画像と PDF は旧サイトの絶対 URL のままで取り込まれる(2026-10-05 に確認)。
取り込みでエラーになったページは、いまと同じく後日の対応にする。

**4-4 移行業者への連絡**
初回は、いまと同じく、シート、ルール、マニュアルを共有する。
2回目からは、取込回ごとに「取り込んだページの範囲」を知らせる。

### 5 その他

5-1〜5-5 は変わらない。
5-4 の禁則文字の登録は、いまも「マニュアルの変換の決まりと禁則文字の変換の決まりが違う」ことが多い。
リニューアル後は、一括処理の変換の決まりも加わるので、3つ(マニュアル、禁則文字、一括処理の案件の設定)を同じ内容に揃える。

### 6 移行作業

**6-1 移行作業** ☆(移行業者、取込回ごと)
アクセシビリティの手直しは、ディレクターが取り込む前に済ませている。
移行業者の作業は、CMS の管理画面での仕上げが中心になる(カテゴリ、ファイル、画像の並び、公開の設定など)。
個別のページの質問は、いまと同じくディレクターに送る。

**6-2 移行後チェック** ☆(ディレクター、取込回ごと)
いまのチェック(移行ページ数の認識合わせ、内容の不備、編集中のステータス、内部リンクが外部リンクのまま残っていないか、ランダムの目視)に、次を加える。

- 移行業者がさらに手直しした箇所を数える。数が多いルールは、共通のルールか案件の設定を見直す。
- CMS のプレビューを miChecker で検査し、本文に起因する指摘が残っていないかを確かめる(`goal2-app/public/michecker-compare.html` で前後を比べる)。

## 取込回の回し方

取込回は、確認画面での確定から移行後チェックまでを、小さな単位で回すためのもの。
1回目の取込回で、2回目以降の大きさと日程を決め直す。

| 週 | ディレクター | 移行業者 |
| --- | --- | --- |
| 1 | 取込回1の一括処理と確定、FTP、取り込み | (待ち) |
| 2 | 取込回2の一括処理と確定、FTP、取り込み。取込回1の移行後チェック | 取込回1の移行作業 |
| 3 | 取込回3 …。取込回2の移行後チェック | 取込回2の移行作業 |
| … | … | … |

## 日程の目安

確認に使える時間は1日5時間、移行作業の期間はおよそ3か月(約60営業日)。

| 移行するページ数 | 1日に確定するページ数 | 1ページの平均時間 |
| --- | --- | --- |
| 1,000 | 17 | 約18分 |
| 3,000 | 50 | 約6分 |
| 10,000 | 167 | 約1.8分 |

10,000 ページの案件は、確認不要のページを開かずに済ませ、さっと確認のページを1分以内で流せることが前提になる。
仮に確認不要が40%、さっと確認が45%(1分)、しっかり確認が15%(10分)とすると、10,000 ページで約 325 時間(1日5時間で約65日)になり、60営業日に収まらない。
この割合は推測なので、4-1 の一括処理の試走で実際の割合と時間を測り、取込回の大きさと日程を決める。
収まらないときは、案件の設定で確認不要の割合を上げる、取込の前の期間を延ばす、の順に考える。

## データの置き場所

| 置き場所 | 置くもの | 誰が書くか |
| --- | --- | --- |
| 移行管理シート | ページの一覧、移行の要不要、カテゴリ、質問と回答、取込データ。「AI 修正」タブに確認の状態、件数、証跡の場所、FTP 上の URL | ディレクター、自治体、一括処理と確認画面(GAS 経由) |
| 共有ドライブ | 案件のフォルダ。ページごとの候補と判断(証跡)、直した HTML、案件の設定、取込回ごとの書き出し | 一括処理と確認画面 |
| FTP 領域 | 取込回ごとの直した HTML | ディレクター |
| CMS | 取り込んだページ | 取り込み(CMS)、移行業者 |
| 共通のルール | アクセシビリティの移行ルール(`a11y-migration-kb/`) | ユーザー(案件をまたいで繰り返し出る決まりを足す) |

## 決まっていないこと、確かめること

- 「AI 修正」タブの列と、既存の「一覧」の列(証跡、移行完了日など)のどちらに何を書くか。
- 共有ドライブの案件のフォルダの形と、FTP 領域のフォルダの形(取込回ごとに分けるか)。
- 移行業者に、直した HTML が取り込まれていることと、手直しが不要になった項目をどう伝えるか(マニュアルの書き換えを含む)。
- 取込回の大きさ(ページ数)を、4-1 の試走の結果からどう決めるか。
- 一括処理と確認画面の結果を、6-2 の移行後チェックのシートにどうつなぐか。
- 旧サイトが移行中に更新されたとき、取込回の前に取り直すかどうか。
- CMS が受け付けるタグと属性(4-1 の CMS 取込試験の結果待ち)。
