# リニューアルの設計書

ディレクター1人が、1案件 1,000〜10,000 ページの旧サイトの本文を、取り込む前に1ページずつ確かめて直す仕組みの設計である。
業務の流れは `FLOW.md`、確認画面(校正台)の見た目と操作は `DESIGN.md` と `review-mockup.html` にあり、この文書はその2つを前提に、仕組みの部品、データの形、作る順番を決める。

CMS の取り込みに関わる節(「CMS に渡す HTML の約束」)は、2026-10-05 の CMS 取込試験の観察と、CMS の取り込みの振る舞いを調べた結果にもとづく。
受け付けるタグと属性は、2026-10-07 の CMS 取込試験で確かめた。

## 前提

2026-10-04〜05 にユーザーが決めたこと、確かめたことを前提にする。

- 利用者はディレクターだけで、案件ごとに1人。確認画面での確認に使えるのは1日5時間。移行業者と承認者は、この仕組みの画面を開かない。
- 規模は1案件 1,000〜10,000 ページ(「移行する」の数)、期間は約3か月、同時に最大6案件。
- すべてのページを目視で確かめる。そのぶん、自動で作る修正の候補の精度を上げる。
- 直した HTML の断片を共有ドライブに写し、ディレクターが FTP 領域に上げ、取込データの移行元 URL を FTP 上の URL に置き換えて、CMS に取り込ませる。
- 画像と PDF は、直した HTML の中では旧サイトの URL のまま残し、FTP には写さない(FTP 側の容量のため)。取り込みの設定の「取得素材ドメイン」に旧サイトのサーバを入れ、取り込みのときに CMS が旧サイトから取得して素材にする(2026-10-05 ユーザー)。旧サイトの公開は、移行が終わったあとに終える調整をしている。
- CMS の取り込みについて確かめたこと(2026-10-05): HTML は断片のままでよい。画像と PDF は、取得素材ドメインが空なら旧サイトの絶対 URL のまま、旧サイトのサーバを入れれば CMS の素材として取り込まれる(2026-10-07)。`#id` のページ内アンカーは残らない。受け付けるタグと属性は、2026-10-07 の CMS 取込試験(`docs/cms-import-tag-test/results/2026-10-07/`)で確かめた。
- CMS の開発チームには、この仕組みのための変更を頼めない。
- 移行管理シートはディレクターが作る。GAS で書き戻してよい。
- ディレクターの PC は、ユーザーの PC とほぼ同じ構成で、ソフトを入れられる。Claude Code を「道具を動かす係」として使う。修正の候補を作る AI は、さくらか Gemini のまま。
- 手放してよいもの: npm 依存ゼロ、Windows 版 `.exe`、Cloud Run。残すもの: データベースを持たない。
- 案件のフォルダは、ディレクターの PC のローカルのディスクに置く。共有ドライブは受け渡しの場所にし、GAS が書く入力を受け取り、一覧、FTP に上げる直した HTML、証跡を写す(2026-10-08 ユーザー。案件のフォルダを共有ドライブに置いた巡回で、遅さと、アイテム数の上限に達したことで続けられなかったため。`trials/2026-10-08-crawl.md`)。

## 名前の付け方

今のアプリは「Goal 1」「Goal 2」「Goal 3」という目標の番号で画面を分けているが、リニューアルではこの名前を使わない。
部品とコマンドは、`FLOW.md` の工程の順に、することの名前で呼ぶ。
ディレクターが工程の番号と名前だけで、どの部品が何をするかを追えるようにするため。

| `FLOW.md` の工程 | 部品とコマンド | すること |
| --- | --- | --- |
| 2-1 ページ一覧 | 巡回 | 旧サイトをたどり、ページの一覧(URL、タイトル)とファイルの一覧を作る |
| 2-2 シート作成 | シートの下書き | 巡回の結果から、移行管理シートで埋める列の案(パンくず、問い合わせ先、ページ種別、重複、新ページタイトル、パターン)を出す |
| 4-5 一括処理 | 取得 | 旧ページを取り、ページの台帳を書く |
| | 型のまとめ | 構造の型でページをまとめ、型ごとの本文の範囲の案を出す |
| | 本処理 | 本文の抽出、候補、安全な候補の採用、残る指摘、取り込みの事前の確かめ、確認の深さ |
| 4-6 確定 | 校正台 | 1ページずつ確かめて確定する。型の本文の範囲を承認する |
| 4-7 書き出し | 書き出し | 確定した HTML と URL の対応表を出す |
| 各工程の前後 | 受け渡し | 共有ドライブの入力を案件のフォルダへ取り込み、一覧、書き出し、証跡を共有ドライブへ写す(案) |
| | 確かめ | FTP 上の URL で HTML が取れることを確かめる |
| 移行中 | 取り直し | 旧ページの更新を見つける |
| 4-3 のあとと 6-2 | 比べ合わせ | 取り込んだページを、旧ページと確定した HTML と比べる |

コマンドは、一括処理という1つの道具のサブコマンド(巡回、シートの下書き、取得、型のまとめ、本処理、書き出し、確かめ、取り直し、比べ合わせ、受け渡し)にする。
今のアプリのフォルダ名(`goal2-app/`)と、それを指す文書は、リニューアルで置き換わるまで変えない。
本番で動いていて、名前を変えると手順書とテストが広く崩れるため。

## 目標と測り方

この仕組みの目標は、2つある。
一つは、ディレクターが1日5時間で、案件の「移行する」ページを期間内に確定できること。
もう一つは、取り込んだあとの移行業者の手直しと承認者の差し戻しを減らすことで、これは候補の精度で決まる。

候補の精度は、次の5つで測る。
どれも校正台の操作と一括処理の出力から自動で数えられるので、ディレクターに記録の手間を増やさない。

| 指標 | 数え方 | 何が分かるか |
| --- | --- | --- |
| 採用率 | 出した候補のうち、ディレクターが採用(編集して採用を含む)した割合。ルール別、案件別 | 当たらないルール。採用率の低いルールは、条件を絞るか、案件の設定で切る |
| 見逃し | 確定した HTML のうち、ディレクターが候補を通さずに手で直した箇所 | 候補が足りないルール。共通のルールに足す材料 |
| 害のある候補 | 却下のうち、理由に「意味が変わる」「行政情報として不正確」を選んだもの | 自動で採用してはいけないルール。1件でも出たら、そのルールを確認不要の判定から外す |
| 残る指摘 | 確定した HTML に miChecker と同じ検査をかけ、本文に残った指摘の数 | 取り込む前に分かる品質。6-2 の本物の miChecker と突き合わせる |
| 取り込み後の手直し | 6-2 の比べ合わせで数える、移行業者がさらに直した箇所と承認の差し戻し | この仕組みの最終の効き目 |

却下のときは、理由を1つ選ぶ(「意味が変わる」「行政情報として不正確」「案件の方針と違う」「直す必要がない」「その他」)。
キー1つで選べるようにし、確認の速さを落とさない。

## 全体の構成

部品は5つで、サーバーを持たない。

```
 移行管理シート(Google スプレッドシート)
   │ ① GAS のメニュー「一括処理の入力を書き出す」
   ▼
 共有ドライブ(受け渡しの場所) ── 入力、一覧、書き出し(FTP に上げる HTML)、証跡
   │ ▲
   ▼ │ 一括処理が、入力を取り込み、一覧、書き出し、証跡を写す
 ディレクターの PC のローカルのディスク
   案件のフォルダ ── 入力、台帳、旧ページ、ページごとの候補と判断、直した HTML、案件の設定、書き出し
   ▲ │                                     ▲ │
   │ ▼ ② 一括処理(ディレクターの PC の Node)  │ ▼ ③ 校正台(Chrome で開く静的 HTML)
   │      巡回、取得、型のまとめ、本処理、     │      型の本文の範囲の承認、
   │      書き出し、確かめ、取り直し、比べ合わせ │      ページを1枚ずつ確かめて確定

 ④ GAS のメニュー「AI 修正を更新」「移行元 URL を置き換える」(共有ドライブに写した一覧を読む) → 移行管理シート
 ⑤ ディレクターが共有ドライブの書き出しを FTP 領域に上げる → CMS が取り込む
```

- ① と ④ の GAS は、シートに付けたメニューから、ディレクターが自分の権限で動かす。Web アプリとして公開しないので、PC から GAS を呼ぶための鍵や認証が要らない。
- ② は、ディレクターが Claude Code に頼んで動かす。
- ③ はファイルを開くだけで動く。サーバーも拡張機能も要らない。
- 案件のフォルダを共有ドライブに置かないのは、1案件4万ファイルの読み書きが共有ドライブでは遅く、アイテム数の上限にも達したため(「危ないところ」)。

この形を選んだ理由は3つある。
利用者がディレクター1人なので、複数の人の同時編集を受けるサーバーが要らない。
1案件 10,000 ページの一括処理は数時間かかる見込みで、ブラウザのタブで回すより、止まったところから再開できるコマンドの方が扱いやすい。
データベースを持たない前提でも、ページごとのファイルと案件ごとの集計ファイルで、必要な問い(残りの数、ルール別の採用率、同じ画像が何ページにあるか)に答えられる。

一括処理は、ディレクターの PC で長く動かせないとき(スリープ、ほかの作業との取り合い)のために、Google Colab でも動かせる形にしておく(Colab では Node と Playwright を入れ直す必要があり、実行時間の上限と切断もある)。Colab で動かすときは、案件のフォルダを Colab から読める場所に移す必要があり、案件のフォルダをローカルに置く決まりと合わない。使うときに置き方を決める。
Colab に移すのは、試走で PC での運用が苦しいと分かったときだけにする。

## 一括処理

一括処理は Node のコマンドである。
旧ページと CMS のページの取得は Node の HTTP で行い、候補のエンジンと miChecker 互換エンジンは Playwright の Chromium の中で動かす。
エンジンを Node 単体(jsdom など)に移さないのは、DOM の振る舞いの差で、miChecker 互換テスト(223 件)と出力テストをやり直すことになるため。
ブラウザのテストがすでに Playwright で動いているので、動かし方の実績もある。
ページの描画に Chromium を使うのは、JavaScript で本文を描くページだけにする。

### 巡回

ページの一覧(`FLOW.md` の 2-1)は、今は Website Explorer で作り、URL とタイトルを移行管理シートに写している。
Website Explorer でうまく取れないサイトでは WebCopy を使い、どちらでも取れないサイトもある(2026-10-07 ユーザー)。
巡回は、これを一括処理のコマンドにし、2つのツールのよいところを取り入れたものである(2026-10-07 ユーザーの依頼)。
一括処理に入れるのは、巡回で取ったページを、あとの取得でそのまま使えるためである。
旧サイトへ取りに行くのが1回で済み、旧サイトへの負荷も減る。

- 始まりの URL からリンクをたどり、`sitemap.xml` も読んで、リンクから届かないページを拾う。リンクを探す場所は、WebCopy に倣って広く取る(要素のリンクに加え、`meta refresh`、`onclick` などとスクリプトの中の `location.href` や `window.open`、選ぶメニューの URL)。
- スクリプトでメニューを描くページは、Chromium で開いてからリンクを拾う(2つのツールとも苦手なところ)。開くのは、始まりのページと、スクリプトがあるのに巡回の範囲のリンクが少ないページだけにする。開くと旧サイトへの要求が増えるため。
- Cookie を巡回のあいだ引き継ぎ、名乗り(ユーザーエージェント)を案件の設定で変えられる(WebCopy)。Cookie を引き継ぐのは Node の取得だけで、Chromium で開くときには渡さない。ログインが要るサイトは扱わない。
- セッションの番号や広告の印など、外してよい URL の項目を外してから、同じページかを決める(WebCopy)。巡回の中でも、値が変わっても中身が同じになる項目を見つけて外す。外すのは、その項目だけが違う URL の組で中身が同じものが3つ以上の別のページで見つかり、中身の違う組が一度も無いときだけである。記事の番号のような項目を、「該当なし」のページが続いただけで外さないため。開いた時刻や乱数を URL に付けるサイトでは、開くたびにリンク先の URL が変わって巡回が終わらない。遠野市の印刷用ページへのリンクの `EntryCode` がこの形だった。1つのページの多くのリンクに同じ長い値で付き、ページごとに値が変わる項目も、開いた時刻の印とみなして外す。
- 大阪市の学校のサイト(Website Explorer と WebCopy で一覧を取れなかった例)のリンクに付く `?tm=…` は、開いた時刻ではなく、リンク先のページの更新日時で、同じページには同じ値が付いていた。2026-10-07 の巡回では問題なく進んだ。このサイトは大阪市の学校のサイトの集まり(学校ごとの道が165以上)で、ページの数そのものが多い。2つのツールで取れなかった理由は分かっていない(トップページが CloudFront の転送で別の道に飛ぶこと、ページの多さなどが考えられる)。
- 階層ごとに順にたどり、階層を始まりから最も少ない手数にする。
- 取りに行くのは、案件の設定で名前を挙げたサーバーだけで、間隔と同時数は取得と同じ設定に従う(`robots.txt`、`sitemap.xml`、Chromium で開くページ、ファイルの大きさを聞く要求も含む)。`robots.txt` で止められた URL は取りに行かない。Chromium で開いたページの中からの要求は、許可したサーバーの名前だけで通し、内部のアドレスの守り(DNS を引いて確かめる)は通さない。開く前に、ページの URL だけを確かめる。
- PDF や画像などのファイルは中身を取らず、ファイルの一覧に URL とリンク元の数だけを書く。
- 中身が同じページに別の URL が付いているもの(遠野市の `index.cfm/…` のような書き方の揺れ、転送)は、一覧に重複先と転送先を書く。
- 取ったページは `crawl/pages/` に置き、取得は、同じ URL で新しさの上限(既定は14日)に収まるものを使う。
- 途中で止めても、続きから再開する。

一覧は、URL、タイトル(`title` 要素)、ディレクトリ、階層、状態、転送先、重複先、更新日、見つけ方、見つけた元の CSV で出し、ディレクターがシートの「一覧」に貼る。
ファイルの一覧には、設定で大きさと更新日を足せる(中身は取らず、ヘッダーだけを聞く。Website Explorer に倣う)。外のサイトへのリンクも一覧にする。
巡回でも取れないサイトのために、オンラインの URL 抽出ツール(digitup の無料 URL 抽出ツール)で取れた例がある(2026-10-07 ユーザー)。
巡回の結果に型のまとめをかけて、2-4 のカテゴライズの手がかりにすることは、まだしていない。

### コンテンツパターンの抽出

案件の仕様書で、全ページを調べて複数ページで構成されているページ群をサブサイト候補として提案し、「コンテンツパターンごとの移行方法定義書」を Excel で出すよう求められることがある(桜井市の例。2026-10-07 ユーザー)。
一括処理の `patterns` のコマンドは、巡回の結果から、この定義書の下書きを作る。

- 巡回で取ったページごとに、構造(要素の道の集まり)とリンクを調べる。
- 群を3通りで見つける。ディレクトリの下のページ、本体(いちばん多い構造の型)と違う作りのページ、リンクのまとまり。リンクのまとまりは、メニューのように多くのページ(3割以上)から張られているリンクを除き、残ったリンクでよくつながっているページの群である。URL がディレクトリで分かれていないサイト(遠野市の `index.cfm/…` など)のために使う。始まりのページを含む群は、サイト全体の入口なので候補にしない。
- 群ごとに、本体と違う作りの割合と、群の中のページどうしのリンクの割合を出し、2つの平均で順位を付ける。上位3つ(案件の設定の `patterns.proposals`)に「サブサイト候補」の印を付ける。
- `crawl/patterns.xlsx` に、サブサイト候補、ページ、構造の型の3枚で出す。移行方法の列は空欄で、ディレクターが書く。
- 1つの巡回に別々のサイトが入っているとき(大阪市の学校のサイトは、学校ごとに別のサイトが並ぶ)は、`patterns --under <URL>` でその URL の下だけを見る。本体の型とテンプレートのリンクを、その下のページだけで決め、`crawl/patterns-<名前>.xlsx` に出す。URL は巡回の記録と同じ形に整え、道の区切りで比べる(末尾の / の有無は問わず、`/e531060` を渡しても `/e5310601/` は入らない)。

名張市図書館の試走では、本体と違う作りのページの群、図書館の案内のディレクトリ、お知らせのディレクトリの3つが候補になった。
候補の順位の付け方が、ディレクターの見立てと合うかは、まだ確かめていない。
リンクのまとまりは、ラベル伝播(隣のページで多い印に合わせる)で作る。巡回の浅いページの印に寄りやすく、始まりのページの群が大きくなって、ほかの群が見つかりにくくなることがある。次の試走で見る。

### 入力

- GAS のメニュー ① が、シートの「移行する」行を、共有ドライブの受け渡しのフォルダの `input/pages.json` に書き出す。一括処理の受け渡しのコマンドが、これを案件のフォルダの `input/pages.json` へ取り込む(GAS はディレクターの PC のファイルを読み書きできないため)。中身は移行管理 ID、旧 URL、ページタイトル、グループ、テンプレートの番号、取込回の番号(シートで指定したもの)。
- 案件の設定 `project/settings.json`(後述)。
- 共通のルール(`a11y-migration-kb/` から作る `rules.jsonl`)。一括処理に同梱する。

シートを直接読まずに書き出したファイルを読むのは、シートの版が上がったときに、どの版で処理したかを証跡に残すため。
書き出すとき、GAS はシートの名前と版、書き出した日時をファイルに入れる。

### 順番

一括処理は、3つの段に分けて動かす。
型のまとめは全ページの取得が済まないとできず、型の本文の範囲の承認はディレクターの作業なので、ページごとに最後まで流す形にはしない。

1. 取得: 対象のページをすべて取り、ページの台帳を書く。
2. 型のまとめ: 取得したページを構造の型にまとめ、型ごとの本文の範囲の案を出す。ディレクターが校正台で範囲を承認する。
3. 本処理: ページごとに、本文の抽出から確認の深さまでを行う。

`FLOW.md` に当てはめると、4-1 の一括処理の試走(1回目)で、抜き出したページの取得と型のまとめまでを行い、型の仮の案を出す。
抜き出したページだけでは、型の大きさ(属するページの数)が案件全体を表さないので、2回目の試走で全ページを取得して型のまとめを回し直し、3-4 で型の本文の範囲を承認して案件の設定に入れる。
4-5 の取込回ごとの一括処理では、その取込回のページを取得し、承認済みの型に当てはめ、本処理を回す。
取込回で新しい型が出たら、本処理の前に校正台で承認するか、承認せずに汎用の判定に回す。

### 取得とページの台帳

取得は、旧 URL からページ全体を取り、`pages/<移行管理ID>/source.html` に保存する。
旧ページは移行中に変わることがあるので、取得した時点の本文を残し、確認と再処理の元にするため。

あわせて、ページの台帳 `pages/<移行管理ID>/fetch.json` を書き、`project/summary.json` にも集める。
旧サイトを、移行管理シートの行と1対1で突き合わせられる台帳に変えておき、取得できない理由、取り込みで失敗する理由、移行中の更新を、同じ台帳の上で数えるため。

- 移行管理 ID、旧 URL、取得の日時、HTTP の状態、最終の URL(転送のあと)、応答の `Last-Modified` と `ETag`。
- 本文のハッシュ(本文の文字を整えてから計算する)と、ページの構造(次の節の「要素の道」の集まりと、その取り方の版)。
- 構造の型、本文の範囲をどう決めたか(型の範囲か、汎用の判定か)。
- 本文にある画像、PDF などのファイル、外部のリンクの一覧と数。
- 対象外の理由(取得できない、本文が空、など)。

取得できなかったページは、`fetch.json` に理由だけを書く。
取得をもう一度動かすと、取得できていないページだけを取り直す(旧サイトが一時的に止まっていたときのため)。

### 構造の型と本文の範囲

同じテンプレートのページは、本文の範囲も同じ場所にあることが多い。
そこで、型のまとめは、構造が似ているページを1つの「構造の型」にまとめ、型ごとに本文の範囲を1つ決めて使い回す。

ページの構造は、body から深さ6までの「要素の道」(body>div#wrap>div.main のような並び)の集まりで表す。
2つのページの集まりの重なり(Jaccard 係数)が 0.8 以上なら、同じ型とみなす(案件の設定の `templates.similarity` で変えられる)。
構造が完全に同じページでまとめる形は、2026-10-07 の試走で採らなかった。
遠野市の97ページが29の構造に割れたため。
メニューで今いる項目のクラス名、一部のページだけにある部品、メニューの開き方が、ページごとに違っていた。

要素の道は、次の決まりで集める。

1. 文字と、文の中の要素(`a`、`span` など)を見ない。
2. 本文を作る要素(段落、見出し、表、リスト、`iframe` など)は、道に入れず、その中にも入らない。本文の作りはページごとに違い、本文が浅い所にあるサイトでは型が割れるため。テンプレートの骨組みは、`div` や `header` などの入れ物の並びで見る。
3. ID とクラスの数字を伏せ、今いる項目に付く状態のクラスの末尾(`Selected`、`current` など)を落とす。
4. 汎用の判定が選んだ本文の要素には頼らない。汎用の判定がページ全体を本文に選んだページで、構造のほとんどが外れたため。

取り方を変えると同じページでも構造の値が変わるので、取り方に版を付ける。
承認した型は、同じ版の構造とだけ比べる。
版が変わったら、型をまとめ直して承認し直す。

型ごとに、一括処理が範囲の案を出し、`project/templates.json` に書く(型の番号、代表の構造、属するページの数と移行管理 ID、試した案とその点、代表のページ、範囲が見つからないページの数、汎用の判定と食い違うページの数)。
案は、型のページで汎用の判定が選んだ要素の中から、文字の比べ合わせで選ぶ。

1. 型の抜き取りのページ(40ページまで)の文字を、段落や表のセルなどのかたまりに分ける。
2. 抜き取りのページの半分以上に出てくるかたまりを、テンプレートの部分(ヘッダー、メニュー、フッター)とみなす。
3. 候補の要素ごとに、ページごとに違う文字のうち要素に入る割合(再現率)と、要素の文字のうちページごとに違う文字の割合(適合率)を測る。
4. ページごとの F 値の平均がいちばん高い要素を案にする。

選ばれた回数の多さや、見つかるページの数と本文の短さで選ぶ形は、2026-10-07 の試走で採らなかった。
汎用の判定は、同じ型の中でもページごとに違う要素を選び、ときにフッターを選ぶ。
そのため、ページ全体やフッターが案になった。
ページごとに違う文字には、題名、パンくず、更新日も入るので、案は本文よりやや広い要素になりやすい。
題名とパンくずは、本文の抽出の掃除で落ちる。
範囲が見つからないページと、汎用の判定と食い違うページの数は、型のページのうち200ページまでの抜き取りで数える。

まだ確かめていないことが2つある。

- 型のまとめは、承認していない型も含めて最も似た型にページを入れるが、本処理は承認した型の中だけで最も似た型を使う。承認していない型に入ったページが、承認した型とも似ていると、`templates.json` の所属と本処理で使う範囲が食い違う。
- 骨組みをレイアウトの表で組んだサイトは、表を道に入れないので道の数が少なく、部品が1つ違うだけで別の型になりやすい。古い自治体サイトで試す。

ディレクターは、校正台で型ごとに代表のページを見て、範囲を承認する。
食い違いの多い型は、範囲を見直してから承認する。
承認した範囲は、案件の設定に型ごとに入る。

ディレクター1人の前提では、型の数がそのまま承認の手間になる。
そこで、属するページが少ない型(たとえば10ページ未満)は承認に回さず、汎用の判定で抜き出す。
シートのテンプレートの番号は型をまとめる手がかりに使い、型と番号が食い違うページは知らせる。
承認したあとも、型の範囲で抜き出せなかったページ、どの型にも当たらないページは、汎用の判定に戻して、しっかり確認に回す。

### 本処理

本処理は、ページごとに、次を順に行う。

1. 本文の抽出: 型の範囲か汎用の判定で、本文を抜き出す。
2. 候補: 共通のルールと案件の設定で、修正の候補を作る。画像の代替テキストなど AI に頼む候補は、ここで、さくらか Gemini を呼ぶ。候補には、箇所とルールから作る変わらない鍵を持たせる。
3. 安全な候補の採用: 「確認不要に入れてよい」と決めたルールの候補だけを自動で採用する。構造を変える候補(表、見出し、リスト)は、決して自動で採用しない。
4. 残る指摘: 直したあとの HTML に miChecker 互換エンジンをかけ、本文に残る指摘を数える。
5. 取り込みの事前の確かめ: 取り込みで失敗する条件と止まる条件を調べる(「CMS に渡す HTML の約束」の「一括処理が前もって確かめること」)。
6. 確認の深さ: 次の節の決まりで、しっかり確認、さっと確認、確認不要に分ける。

結果は、すべての段が終わってから `pages/<移行管理ID>/candidates.json` に書く。
本処理を終えたら、`project/summary.json`、`project/metrics.json`、`project/status.csv` を書き直す。
4-5 のあとに、「AI 修正」タブへ確認の深さと取り込めない理由を写せるようにするため。

### 再開と再処理

- 再開: 取得は `fetch.json` に取得の成功があるページを、本処理は `candidates.json` があるページを飛ばす。`candidates.json` はすべての段が終わってから書くので、途中で止まったページは、同じコマンドをもう一度動かせばやり直される。ただし、`fetch.json` に「旧ページが変わった」の印があるページ(`candidates.json` に記した本文のハッシュが台帳と違うページ)は、`candidates.json` があっても本処理をやり直す。
- 再処理: 案件の設定や共通のルールが変わったとき、まだ確定していないページだけを処理し直す。判断の引き継ぎは、校正台が `decision.json` の判断と新しい候補を鍵で突き合わせて行い、一括処理は `decision.json` を書かない。鍵が合わない候補(取り直しで本文が変わったページなど)は引き継がず、新しい候補として見せる。確定済みのページには遡らない(`FLOW.md` の 3-4)。

### 取り直し

旧サイトは移行中にも更新される。
取り直しは、旧 URL を取り直し、本文のハッシュを台帳の値と比べて、変わったページを見つける。
台帳の `Last-Modified` と `ETag` で条件付きの取得を行い、変わっていないページは本文を取らずに済ませる。
10,000 ページを毎回取り直すと、旧サイトに数時間の取得の負荷がかかるため。

本文が変わったページについて、一括処理は、`source.html` と `fetch.json`(取得の日時、ハッシュ)を書き直し、日付、金額、連絡先、期限の変わった箇所を抜き出して `pages/<移行管理ID>/changes.json` に書き、`fetch.json` に「旧ページが変わった」の印を付ける。
校正台が印を1万個のファイルから探さずに済むよう、`project/summary.json` も書き直す。
変わった箇所の扱いは、ページの状態で分ける。
ページの状態は、校正台の `review-index.json`、書き出しの `export/<取込回>/url-map.csv`、取込回の記録 `import-rounds.json` を突き合わせて決める。後回しで取込回がずれるので、`input/pages.json` の取込回は使わない。

| ページの状態 | 扱い | 誰が |
| --- | --- | --- |
| 未確定 | 新しい本文で本処理をやり直し、印を消す | 一括処理 |
| 確定したが、まだ取り込まれていない(FTP に上げたが取り込み前を含む) | 確定を外して待ち行列に戻し、変わった箇所を指示として見せる。そのあと一括処理が本処理をやり直して印を消し、ディレクターがもう一度確定したら、書き出しで上げ直す(CMS は取り込みの最初の段階で HTML を取得するので、取り込みの前なら上げ直しが効く) | 校正台(確定を外す)、一括処理(本処理と印) |
| 取り込み済み | 変わった箇所を、「AI 修正」タブの「旧ページの更新」の列に書き、4-4 の連絡で移行業者に知らせる。CMS は同じ移行管理 ID で HTML を取得し直さないので、移行業者が CMS の画面で直す。印は消さない | 一括処理(列の中身)、ディレクター(連絡) |

取り直しは、取込回ごとに書き出しの数日前と直前の2回、旧サイトの更新が多い案件では加えて週に1回、回す。
直前の1回だけでは、確定を外す、本処理、確認し直すの3つが書き出しまでに入らないため。

### 速さの見込み

10,000 ページで、取得に1ページ1〜2秒(旧サイトに負荷をかけないよう、同時に取るのは2ページまで)、エンジンに1ページ1秒前後、AI の呼び出しは画像の数による。
取得とエンジンだけなら数時間、AI を含めると半日から1日になる見込みで、これは推測なので試走で測る。
旧サイトへの取得の間隔と同時数は、案件の設定で変えられるようにする。

## 確認の深さの決め方

本処理は、ページごとに確認の深さを1つ決める。
決め方は、そのページの候補のうち一番重いもので決まる。

| 確認の深さ | 入る条件 | ディレクターがすること |
| --- | --- | --- |
| しっかり確認 | 構造を変える候補(表、見出し、リスト)、意味に関わる候補(本文の言い換え、代替テキストの新規作成)、「確かめる点あり」の候補、本文の抽出が汎用の判定に戻った、取り込みの事前の確かめに引っかかった | 修正前と修正後を読んで判断する |
| さっと確認 | 表記の揃え、既存の代替テキストの手直し、リンクの文言の補正など、小さな直しだけ | 差分を見て採用する |
| 確認不要 | 候補が無い、または確認不要に入れてよいルールの候補だけ | 開かない。取込回ごとに校正台でまとめて確定する |

確認不要に入れてよいルールは、初めは空にし、次の条件を満たしたルールだけを足す。

- 試走と取込回で、そのまま採用した割合が 99% 以上(編集して採用は数えない。却下と編集が100件に1件以下)。
- 害のある候補が0件。
- ルールの性質として、意味を変えない(全角英数字を半角にする、など)。

ルールを確認不要に入れるか外すかは、案件の設定で案件ごとに決め、共通のルールの側では「入れてよい候補」の印だけを持つ。
害のある候補が1件出たら、一括処理は `project/metrics.json` に「確認不要から外すべきルール」として書き、次の本処理からそのルールの自動の採用を止める。
外すことの確定は、校正台でディレクターが行い、校正台が案件の設定を書き換える。
一括処理は案件の設定を書かない。

確認不要のページは開かれないので、確認不要に入れたルールの害は、そのままでは見つからない。
そこで、確認不要のページのうち一部(たとえば50ページに1ページ)を抜き取って、さっと確認に回す。
6-2 で数える取り込み後の手直しも、確認不要に入れたルールの見張りに使う。

## 校正台

校正台は、`review-mockup.html` を本物のデータで動くようにしたものである。
見た目と操作は `DESIGN.md` に従う。
ページの確認のほかに、型の本文の範囲の承認と、確認不要のページのまとめての確定を行う。

### ファイルの読み書き

Chrome の File System Access API で、ディレクターの PC のローカルのディスクにある案件のフォルダを開く。
初めに一度フォルダを選べば、次からはブラウザが選んだフォルダを覚えている(許可の確認は出る)。

- 読む: `input/pages.json`、`project/templates.json`、`pages/*/fetch.json`、`pages/*/candidates.json`、`pages/*/changes.json`、`pages/*/decision.json`、`project/settings.json`、`project/summary.json`、`project/metrics.json`。
- 書く: `pages/<移行管理ID>/decision.json`、`project/review-index.json`、`project/import-rounds.json`、案件の設定(`project/settings.json`)。

採用、却下、確定のたびに、その場で書く。
「保存」のボタンは置かない。

10,000 ページ分のファイルを開くたびに読むと遅いので、一覧に要る項目は一括処理が `project/summary.json` にまとめ、校正台はまずそれだけを読む。
確定の状態は `decision.json` にあり、`summary.json` には入らないので、校正台は自分だけが書く索引 `project/review-index.json`(ページごとの状態と確定日)を持ち、判断のたびに書き足す。
ページの中身は、そのページを開いたときに読む。

案件のフォルダはローカルのディスクに置くので、ファイルの読み書きにネットワークを待たない。
共有ドライブへ写すのは一括処理の役目で、校正台は共有ドライブを開かない(証跡を写す時期は「決めてほしいこと」)。

校正台は `file://` で開く前提なので、選んだフォルダを覚える仕組みと許可の確かめが Chrome で期待どおりに働くかを、段 3 の初めに確かめる。
書体は、校正台の HTML と同じフォルダに置いて読み込む(`DESIGN.md` の「自分のサーバーに置く」は、この形に読み替える)。

### 判断の記録

`decision.json` には、候補ごとの判断(採用、編集して採用、却下とその理由、後回しと質問の下書き)、ページの確定の時刻、確定した HTML、ディレクターが手で直した箇所の差分を書く。
今の証跡の形(候補、判断、修正前後、理由、関連する WCAG)を引き継ぎ、6-2 や顧客への説明に使えるようにする。

### 一括の決定

右の列の指示から「このルールを案件の全ページで採用」を押すと、校正台は案件の設定にその決定を書く。
まだ開いていないページのファイルは書き換えず、ページを開いたときに案件の設定から「案件で採用」と表示する。
画像の代替テキストも同じで、同じ画像の URL が案件のほかのページにあれば、決めた代替テキストを使う。
この一括の決定は、確定済みのページには効かない。
自治体の方針に関わる決定は、ここでは決めず、自治体に確かめる(`FLOW.md` の 3-4)。

### 確認不要のページの確定

確認不要のページは開かないが、書き出すには確定した HTML が要る。
そこで、校正台に「確認不要のページをまとめて確定」を置く。
押すと、指定した取込回の確認不要のページについて、自動で採用した候補と案件の一括の決定を当てた HTML を組み立て、`decision.json` と `review-index.json` に「まとめて確定」として書く。
ディレクターが押す操作にするのは、確認不要のページも、確定した人と時刻を証跡に残すため。

## 案件の設定

案件の設定は `project/settings.json` の1つのファイルで、共通のルールの上に重ねる。
共通のルールそのものは書き換えない。

- 本文の範囲: 構造の型ごとに承認した範囲。テンプレートの番号は型をまとめる手がかりとして持つ。
- CMS のページの本文の範囲: 取り込んだあとのページで本文がある要素。比べ合わせに使う。
- 表記の決まり: 日付、電話番号、単位など、自治体ごとの書き方。
- ルールごとの扱い: 自動で採用(確認不要に入れる)、確認する、使わない。
- 辞書: 画像の URL と代替テキストの対応、同じ表記の置き換え。
- 取り込みの設定の写し: 本文の範囲、部品に分けるかどうか、文中のリンクと画像を外に出すかどうか(リニューアルでは「そのまま」)、旧 CMS からの移行用の取り込み方が有効かどうか、取得素材ドメイン(旧サイトのサーバ)。取込環境への設定は、ディレクターが行う。
- 取り込みの決まり: 強制アクセシビリティチェックに当たる文字、禁則文字の変換(5-4 と揃える)。
- 取得の決まり: 旧サイトへの取得の間隔と同時数、除く URL、取りに行ってよいサーバ(「取得の守り」の節)。
- FTP の URL の頭。

変更は `project/settings-history.jsonl` に履歴を残す(変更した日時、誰が、どの画面から)。
案件の設定で繰り返し出る決まりは、ユーザーが既存のトリアージの手順で共通のルールに足す。

## シートへの書き戻し

シートへの書き戻しは、GAS のメニューで行う。
PC から GAS を呼ばないので、鍵や認証の置き場が要らない。

- 「一括処理の入力を書き出す」: 「移行する」行を、共有ドライブの `input/pages.json` に書き出す(前述)。
- 「AI 修正を更新」: 一括処理が共有ドライブの `lists/` に写した `status.csv`(移行管理 ID ごとの状態の一覧)を読み、「AI 修正」タブに写す。10,000 行でも1つのファイルなので、GAS の実行時間の上限(6分)に収まる。
- 「移行元 URL を置き換える」: 一括処理が共有ドライブの `export/<取込回>/` に写した `url-map.csv`(移行管理 ID、旧 URL、FTP 上の URL)を読み、取込データの移行元 URL を置き換える。置き換える前の値は別の列に残し、戻せるようにする。

「AI 修正」タブの列は、次を案にする。
既存の「一覧」の列には書き込まない。

| 列 | 中身 |
| --- | --- |
| 移行管理 ID | 「一覧」と突き合わせる鍵 |
| 取込回 | 書き出した取込回の番号 |
| 確認の深さ | しっかり確認、さっと確認、確認不要 |
| 状態 | 未処理、取得できない、未確認、後回し、確定、書き出し済み、取り込み済み |
| 取り込めない理由 | ページタイトルが60字以上、グループが空欄、取得できない、など |
| 指示の数、採用、却下 | 件数 |
| 残る指摘 | 確定した HTML の本文に残る指摘の数 |
| 質問の下書き | 後回しの指示に付けた下書き |
| 旧ページの更新 | 取り込み済みのページで旧ページが変わった箇所(取り直しで見つけたもの) |
| 旧 URL、FTP 上の URL | 対応 |
| 確定日 | 校正台で確定した日 |
| 証跡の場所 | 共有ドライブに写した証跡のファイル(取込回ごと)。ディレクターの PC の案件のフォルダは、ほかの人が開けないので書かない |

## 書き出しと FTP

取込回の書き出しは、一括処理の書き出しのコマンドで行う。

1. 指定した取込回の、確定したページを集める(`review-index.json` を読む)。後回しの指示が残るページは外す。
2. 確定した HTML を `export/<取込回>/<移行管理ID>.html` に書く。文字コードとファイルの形は、CMS が取り込める形にする(次の節)。案件の取り込みの設定で「部品に分ける」が有効なときだけ、リンクだけの段落のリンクのうち「移行するページへのリンク」を、そのページの FTP 上の URL に書き換える(次の節の「リンク」)。画像と PDF の URL は書き換えない。
3. `export/<取込回>/url-map.csv` を書く。FTP 上の URL は、案件の設定の FTP の URL の頭に移行管理 ID をつないで作り、取込回を含めない。後の取込回で取り込むページへのリンクを、先に書き換えておけるようにするため。
4. `project/status.csv` を書き直す。
5. `export/<取込回>/` と `status.csv` を共有ドライブの受け渡しのフォルダに写し、ファイルの数を照らしてから、写し終わりの印を置く(案)。

ディレクターは、写し終わりの印を確かめてから、共有ドライブの `export/<取込回>/` の中身を、FTP 領域の案件のフォルダ(取込回で分けない)に上げ、シートのメニューで移行元 URL を置き換える。
FTP に上げる作業を一括処理から行わないのは、FTP の接続先と認証を PC の外に置きたくない(ディレクターの FTP の道具に任せる)ため。
上げたファイルが FTP 上の URL で取れることは、一括処理の確かめのコマンドで、URL を順に取って確かめる。

CMS に取り込んだら、ディレクターは校正台で「この取込回を取り込んだ」と取り込みの日を記録する。
校正台はこれを `project/import-rounds.json` に書き、取り直しと比べ合わせと「AI 修正」タブの状態(取り込み済み)が読む。
`status.csv` は一括処理が書くので、取り込みの日を記録したあとは、比べ合わせのコマンドを動かし、一覧を共有ドライブに写してから「AI 修正を更新」を押す。

## CMS に渡す HTML の約束

この節は、CMS 取込試験(2026-10-05 と 2026-10-07。結果は `docs/cms-import-tag-test/results/2026-10-07/`)と、CMS の取り込みの振る舞いを調べた結果(非公開のメモ)にもとづく。
試験でまだ確かめていないものには「試験で確かめる」と書いた。
取り込みの振る舞いは、案件ごとの取り込みの設定で変わる。
2026-10-07 の試験は、部品に分ける(各項目挿入: する)、文中のリンクと画像を外に出す(複数行HTML内素材処理: 素材型に移動)、旧 CMS からの移行用の取り込み方が有効(地図の部品のキーが空でない)の設定で行った。最後の設定が有効なときは、`p`、`iframe`、見出しと `a` の `id` が残る。試験ページ 15(表)と、03(リンク)、04(画像とファイル)は、文中のリンクと画像を外に出さない設定(そのまま)でも取り込んだ。

リニューアルでは、複数行HTML内素材処理を「そのまま」にする(2026-10-07 ユーザー)。「素材型に移動」では、段落、箇条書き、表の中のリンクと画像が外に出され、元の場所には文字だけが残り、表の意味が壊れるため。取込環境の取り込みの設定は案件ごとのもので、ディレクターが案件の取込環境に設定し、案件の設定に写す。この節は「そのまま」を前提に書き、「素材型に移動」での振る舞いは比べるために残す。設定が違う案件では試験をやり直す。

### 取り込みの進み方

- 取り込みは、担当者が CMS の画面のボタンで始める。日時を指定して自動で動く仕組みは無い。`FLOW.md` の「取り込み日」は、運用で決める予定日である。解析、登録、設定の保存の前には、ブラウザの確認ダイアログが出る。
- CMS は、取り込みの最初の段階で移行元 URL の HTML を取得し、同じ移行管理 ID では取得し直さない。取得した時点で HTML が決まるので、そのあと FTP 上の HTML を直して置き直しても反映されない。だから、FTP に上げるのは確定したページだけにし、取り込んだあとの直しは CMS の画面で行う。
- 4-1 の取り込みテストで、本番と同じ取込環境に同じ移行管理 ID でページを登録すると、その行は旧サイトの HTML のまま決まってしまう。取り込みテストと本番とで、取込環境か移行管理 ID を分ける。
- 試験では、1回の登録で 12 件を選んだところ 10 件で止まり、残りは処理されなかった(上限の決まりは調べていない)。取込回の登録は 10 件以下ずつ選び、残った行が無いかを確かめる。
- 取り込みは、本文のリンク先に実際に接続しに行く。応答しないサーバへのリンクがあると、取り込みが長く止まる見込み(応答の速いサーバへのリンクだけのページは、十数秒で終わった。止まるかは試験で確かめる)。
- 取り込み結果の一覧には、成功した行にも注意が書かれる。
- 取り込み用の CSV は、22列の見出しの名前と並びが一致し、Shift_JIS で保存する。素材保存先グループは、取込環境に存在するグループの名前でないと、その行がチェック NG になる(試験で確認)。

### 文字が消えたり増えたりしないようにする

取り込みのエラーにならずに、文字が消えたり増えたりする。
気づきにくいので、本処理の「候補」の段で、次の項目をルールの候補として出す。
機械で直せるもの(電話番号のリンクを文字にする、`href` の無いリンクを文字にする、リンクの中のタグを外す、ファイルのリンクの種類と容量の表記)は、案件の設定の「ルールごとの扱い」で、初めから自動で採用にしてよい。
判断が要るもの(代替テキスト、`<` `>` の言い換え)、構造を変えるもの(画像のリンクと文字のリンクを分ける)は、校正台で確かめる。

- 電話番号のリンク(`tel:`)は、番号の文字ごと消える。リンクを外し、番号を文字として書く。
- `href` の無い `a`、`href="javascript:…"` の `a` は、リンクの文字ごと消える。リンクを外して文字にする。
- 本文の `&lt;` `&gt;` で書いた「<」「>」は、タグとして読まれて消える。全角の「＜」「＞」か、言い換えにする。
- リンクの中には文字だけを入れる。「そのまま」の設定では、ほかの要素を含むリンクの中身(`<p>`、`<strong>`)が、タグのまま文字として表示された(試験で確認)。リンクの中の `strong` などは外す。
- 画像と文字の両方を含むリンクは、どちらの設定でも、リンクの文字が消えて画像のリンクだけになった(試験で確認)。画像のリンクと文字のリンクは、別々のリンクにする。
- 画像の `alt` 属性が無いと、`alt=""`(装飾の画像)になる。意味のある画像には必ず代替テキストを書き、装飾の画像だけを空にする。

ファイルのリンクの種類と容量は、リンクの置き場所で扱いが変わる(「そのまま」の設定。試験で確認)。

| ファイルのリンクの置き場所 | 取り込んだあと | 一括処理がすること |
| --- | --- | --- |
| ファイルのリンクだけの段落 | ファイルのリンクの部品になり、「(PDFファイル: 30.2KB)」のような種類と容量の文字が付く | リンクの文字から、元からある種類と容量の表記を外す。外さないと二重に表示され、元の容量が実際と違えば誤った情報が残る |
| 文の中、箇条書きの中、表の中 | 元の場所にリンクのまま残り、種類と容量の文字は付かない(容量の属性とファイルの種類のクラスは付くので、公開側の見た目でアイコンが出るかは分けていない) | リンクの文字に、種類と実際の容量を書く。書式は、CMS の部品の表示に寄せて「（PDFファイル：1.9MB）」とする。容量は、一括処理が事前の確かめでファイルを取りに行ったときの大きさを使う。手で書いた容量は、CMS で素材を差し替えると古くなる |

共通のルール「ファイルのリンクの表示文字」(`a11y-migration-kb/rules/file/file-display-text.md`)に、この置き場所の条件を書いた(2026-10-07)。

「そのまま」の設定でも、リンクだけの段落はテキストリンクの部品に、画像だけの段落と段落の外の画像は画像の部品になる(試験で確認)。部品に分ける(各項目挿入: する)設定が効いている。

比べるために、「素材型に移動」の設定での振る舞いを書いておく(試験で確認)。

- 段落、箇条書き、表の中のリンクと画像は、部品として外に出され、元の場所には文字だけが残る。リンクの文字が二重に読める。
- 段落の中の画像は、元の場所に代替テキストが文字として入る。
- 表では、どの行のファイルや画像かが表から分からなくなり、様式の一覧のような表の意味が壊れる。
- ファイルのリンクは、置き場所によらずファイルのリンクの部品になり、種類と容量の文字が付く。

### HTML の形

- HTML の断片のままでよい(試験で確認)。ファイルの先頭で文字コードを宣言する(宣言が無いと UTF-8 として読まれる見込み。試験で確かめる)。
- FTP 上の URL は、半角英数字と一般的な記号だけで書き、サーバ名の後に必ずパスを付ける。移行管理 ID もこの文字だけで作る。
- 本文は、案件で決めた本文の範囲(決まった ID やクラスの要素)で囲む。範囲が見つからないと、ファイル全体が取り込まれる。
- 見出しは `h2` から始め、レベルを飛ばさない。`h1` は中身ごと消え(除外範囲のタグ `h1` による)、`h2` が無いと見出し全体が1段ずつ繰り上がる(試験で確認。表のセルの中の見出しも繰り上がる)。見出しの中の `strong` は消える。
- 残る要素(試験で確認): `br`、`strong`、`em`、`sup`、`sub`、`code`、`q`、`cite`、`blockquote`、`pre`、`ul`、`ol`(`start`)、`li`、`dl`、`dt`、`dd`、`span lang`、`table`、`caption`、`thead`、`tbody`、`tfoot`、`th scope`、`colspan`、`rowspan`、表の `summary`。`p`、YouTube と地図の `iframe`、見出しの `id` は、旧 CMS からの移行用の取り込み方が有効な案件では残り、無効な案件では消える見込み(試験で確かめる)。段落の区切りが `p` に頼れない案件では、改行も入れておく。
- 消える要素(中の文字は残る): `s`、`del`、`ins`、`mark`、`abbr`、`time`、`kbd`、`ruby`、`hr`、`address`、`section`、`article`、`aside`、`figure`、`figcaption`、`details`、`font`、`div` の入れ子など。意味を伝えるものは、文字で書き直す(ルビは括弧書き、取り消し線は「(削除)」などの文字)。
- 消える属性: `class`、`id`(見出し以外)、`style`(すべて)、`title`、`role`、`aria-*`、`data-*`、`dir`、`ol type`、表の `headers` と `th` の `id`、`th abbr`、表とセルの古い属性(`summary` は残る)と `style`、画像の部品に出された画像の `width` と `height`。`align` 属性だけは `style="text-align: …"` に変換されて残る。意味を色や位置や属性だけで伝えない。
- 段落の `lang` は、`<span lang="…"><p>…</p></span>` のように外から包む形になる。外国語の部分は、段落の中の `span lang` で書く。
- `b`、`i`、`u`、`small` は残るが、CMS の公開前のチェックで止まることがある。`strong`、`em` を使う。
- `script`、`style`、`noscript`、フォーム、インラインの `svg`、`video`、`audio`、`object`、`embed`、`canvas`、`math` は入れない。インラインの `svg` は要素ごと消える。
- ふつうのリンクとファイルのリンクは、プレビューで `target="_blank"`(新しいウィンドウで開く)が付いていた(画像ファイルへのリンクには、素材型に移動では付かず、そのままでは付いた)。部品の設定か公開側の描画かは分けていないので、移行業者が CMS で直すかどうかを、案件で決める。
- `#id` のページ内リンクは、`移行元URL#id` の外部リンクになる(試験で確認)。共通のルール「ページ内アンカーリンク」に沿って、文章で示す形に直す。

### 画像とファイル

- 画像と PDF は、直した HTML の中では旧サイトの絶対 URL のまま残す(「前提」)。
- CMS は、移行元 URL と同じサーバの画像とファイルを素材として取り込む。移行元 URL を FTP 上の URL に置き換えると、旧サイトは別のサーバになるので、取り込みの設定の「取得素材ドメイン」に旧サイトのサーバを入れて、旧サイトの画像と PDF も素材として取り込ませる(試験で確認。画像、PDF、Excel、Word がすべて素材になり、同じ URL のものは1つの素材が使い回された)。
- 取得素材ドメインに何かを入れると、入れていない別のサーバの画像も素材として取りに行く(試験では、別のサーバ1つの画像1枚で確かめた)。だから、取り込みの事前の確かめは、本文のすべての画像とファイル(外部のサーバのものを含む)を対象にする。
- 取得素材ドメインが空のときは、別のサーバの画像は素材にならず、元の URL のまま残る。試験では、画像の多いページ(段落の外、`figure` の中、表の中、リンクの中の画像を含む)だけが「素材画像Noが取得できませんでした」でページ全体が登録されなかった。画像の部品に振り分けられた画像が素材でないためと推測する。
- SVG と WebP の画像ファイルは、素材として取りに行くと「画像の登録に失敗しました」になり、ページ全体が登録されない(試験で確認)。`data:` の画像は `src` が消える。どれもページの理由として知らせ、PNG か JPEG の画像に差し替えるかを、自治体か移行業者と決める。
- 取得できない画像があると、部品に分ける設定ではそのページ全体が登録されない。取得できないファイルは、エラーとして報告されずに空のファイルとして登録されることがある(試験で確かめる)。だから、一括処理は、本文の画像とファイルがすべて取れることを前もって確かめ、取れないものをページの理由として知らせる。
- 素材のファイル名は、半角英数字、ハイフン、アンダースコア以外を含むとき、既存の素材と同じ名前のとき(試験で確認)、取り込みの設定によっては、乱数の名前に変わる。
- 拡張子で終わらない、またはクエリ文字列の付いたファイルの URL は、素材として判定されないことがある。旧サイトの URL をそのまま残すので一括処理では直せず、ページの理由として知らせる。

### リンク

- CMS は、本文のリンクがほかの行の移行元 URL と一字一句同じ(`http` と `https`、末尾の `/`、`index.html` の有無、`#` 以降まで)で、その行の取り込みが済んでいるときだけ、リンクを CMS の内部リンクに変える。変換は、取り込みのあとに別のボタンで行い、部品に分ける設定のときだけ働く(試験で確かめる)。
- 移行元 URL を FTP 上の URL に置き換えると、本文に残った旧 URL のリンクは、どの行の移行元 URL とも一致しなくなり、内部リンクに変わらない。
- そこで一括処理は、案件の取り込みの設定で「部品に分ける」が有効なときだけ、書き出すときに、テキストリンクの部品になるリンク(リンクだけの段落のリンク)のうち、「移行するページへのリンク」を、そのページの FTP 上の URL に書き換える。他のページの見出しへのリンク(`#` 付き)は、`#` 以降を落として書き換える。後の取込回で取り込むページへのリンクも、取り込みが済んだあとに変換のボタンをもう一度押せば変わる。
- 「部品に分ける」が無効な案件では書き換えず、旧 URL のまま残す。FTP は一時的な置き場なので、FTP 上の URL が公開ページに残ると旧 URL より悪い。旧 URL のままなら、6-2 の「内部リンクが外部リンクのまま残っていないか」のチェックで見つかる。
- 相対パスのリンクは、移行元 URL(FTP)を基準にした絶対 URL になる(試験で確認)。一括処理は、書き出す前に、相対パスのリンクを旧ページの URL を基準にした絶対 URL に直す。
- 「そのまま」の設定では、リンクだけの段落以外のリンク(文の中、箇条書きの中、表の中、見出しの中)は、部品にならずに本文のかたまりに残る(試験で確認)。CMS の取り込みの振る舞いの調べでは、本文のかたまりに残ったリンクには内部リンクの番号の属性が足されるだけで、リンク先は変わらない見込みである(実機では未確認)。だから、これらのリンクは FTP 上の URL に書き換えず、旧 URL のまま書き出す。FTP 上の URL のまま公開されることを避けるため。旧 URL のまま残ったリンクは、6-2 の「内部リンクが外部リンクのまま残っていないか」のチェックで見つけ、移行業者が CMS で直す。
- 「リンクだけの段落」は、本文の直下の `p` で、空白を除いた中身が1つの `a` だけで、`a` の中身が文字だけのものとする(本文の直下の裸の `a` は、書き出す前にこの形に直す)。試験では、この形と、段落の外に置いた段落を丸ごと囲むリンクが部品になり、1つの段落に2つのリンク、文の中、箇条書き、表、見出しの中のリンクは本文のかたまりに残った。文字だけを入れた本文の直下の裸の `a`、`<br>` や `strong` を伴う形、`div` の中の形は確かめていない(裸の `a` は部品になる見込み)。この形に当てはまらないものは、FTP 上の URL に書き換えない。部品になるのに旧 URL のまま残っても 6-2 で見つかるが、部品にならないのに FTP 上の URL に書き換えると、そのまま公開に残るため、迷うものは書き換えない側に倒す。
- 内部リンクの変換は、確かめていない。変換のボタンは取込環境全体(ほかの人の行を含む)を対象に動き、別の取込環境でも同じなので、ボタンを押す時期と範囲を、取込環境を使う人と決めてから確かめる(「決めてほしいこと」)。比べ合わせで、公開ページに FTP のサーバへのリンクが残っていないかを確かめる。
- 移行しないページへのリンクと、外部のリンクは書き換えない。

### 一括処理が前もって確かめること

取り込みで失敗する条件と止まる条件を、本処理の「取り込みの事前の確かめ」で調べ、ページの理由として記録する。

- ページタイトルが60字以上、機種依存文字や禁則文字を含む(その行は登録されない)。グループが空欄か、取込環境に無いグループ。
- 取得できない画像とファイル(外部のサーバのものを含む)、SVG、WebP、`data:` の画像、拡張子で終わらないかクエリ文字列の付いたファイルの URL。
- 応答しない、または応答の遅いサーバへのリンク(短い時間で区切って応答の番号だけを見る)。該当するページは、まとめて小さな取込回に入れるか、取り込み担当者に知らせる。
- 上の「文字が消えたり増えたりしないようにする」の項目(電話番号のリンク、`href` の無いリンク、文字としての `<` `>`、リンクの中のタグ、画像と文字の両方を含むリンク、ファイルのリンクの種類と容量の表記(外すか書くかはリンクの置き場所で決まる)、`alt` の無い画像)。候補として出し、採用されずに残ったものを理由として知らせる。
- `h1` がある、`h2` が無い、見出しのレベルが飛ぶ。
- CMS の公開前のチェックで止まる表記(「TEL」「FAX」などの略記、日付の区切り、全角英数字、`b` `i` `u` など)。どの項目で止まるかは顧客ごとの設定なので、案件の設定に、その顧客で有効な項目を写す(5-4 と揃える)。

## 取り込み後の比べ合わせ

CMS に取り込んだページを取り直し、旧ページ、確定した HTML、取り込んだあとのページの3つを比べる。
取り込みの振る舞いで崩れる箇所を、目視の抜き取りでなく、全ページの数で見つけるため。

比べ合わせは、取込回ごとに2回行う。

- 取り込みの直後(4-3 のあと、6-1 の前): 取り込みで崩れた箇所を見つける。崩れが多ければ、次の取込回の前に「CMS に渡す HTML の約束」と一括処理を直す。
- 6-2 の移行後チェック: 1回目の結果と比べ、移行業者がさらに直した箇所を数える(指標「取り込み後の手直し」)。取り込みの崩れと移行業者の手直しを混ぜないため。

比べるものは次のとおり。

- 本文: 確定した HTML と取り込んだあとの本文の文字の差。消えた段落や、繰り上がった見出しを見つける。取り込んだあとのページの本文は、案件の設定の「CMS のページの本文の範囲」で抜き出す。
- 画像と PDF: CMS の素材になったか、旧サイトの URL のまま残ったか。素材のファイルの大きさが0でないか。
- リンク: 内部リンクに変わったか、旧 URL や FTP のサーバへのリンクが残っていないか。
- ページ内アンカー: 確定した HTML で文章に直した箇所が残っているか。

比べる先のページの URL は、CMS の取り込み結果の一覧から取る。
プレビューの URL にログインが要るときの取り方(ディレクターが自分で開いたブラウザを使うかなど)は、段 6 の前に確かめる。
ログインの情報を、一括処理と Claude Code に渡さない。

## 取得の守り

旧サイト、FTP、CMS からの取得と、リンク先の応答の確かめは、どれも同じ取得の部品で行う。
取りに行ってよい範囲を、用途で2つに分ける。

- ページと素材の取得: 案件の設定で名前を挙げたサーバ(旧サイト、FTP、CMS)だけ。
- リンク先の応答の確かめ: 外部のサーバも対象にするが、短い時間で区切り、応答の番号だけを見て本文は取らない。

どちらも、取得の間隔と同時数、1ページの大きさの上限、やり直しの回数、止めたところからの再開を決めておく。
今の URL 取得の API にある、内部のネットワークのアドレスを取りに行かせない守り(SSRF 対策)も引き継ぐ。
CMS の取込環境が社内のネットワークのアドレスにあるときは、案件の設定で名前を挙げたサーバだけを、この守りの例外にする。

## 採らないもの

- AI の呼び出しの履歴を圧縮する仕組み: 修正の候補を作る AI の呼び出しは、ページごと、候補ごとに独立した1往復で、圧縮する履歴が無い。
- AI による確認の深さの決定とルールの省略: 共通のルールは、すべてのページに決まった手順でかける。AI で型を分ける、レビューの順番を決めるといった補助を足すとしても、表示の順番を決める範囲にとどめ、本文を外部のサービスに送らずに、構造の特徴だけで試す。

## 案件のフォルダの形

ディレクターの PC のローカルのディスクに、案件ごとに次のフォルダを作る。

```
<案件>/
  input/
    pages.json             GAS が書き出す「移行する」行と、シートの名前、版、日時(共有ドライブから取り込む)
  crawl/                   巡回の結果。ページの一覧、ファイルの一覧、ページの写し、コンテンツパターン(一括処理)
  project/
    settings.json          案件の設定(校正台と人が書く)
    settings-history.jsonl 案件の設定の変更履歴
    summary.json           台帳と一覧に要る項目の集計、「旧ページが変わった」の印(一括処理)
    templates.json         構造の型、範囲の案、代表のページ、食い違いの数(一括処理)
    status.csv             「AI 修正」タブへ写す一覧(一括処理)
    metrics.json           精度の指標と、確認不要から外すべきルール(一括処理)
    review-index.json      ページごとの確定の状態と確定日(校正台)
    import-rounds.json     取込回ごとの取り込みの日(校正台)
  pages/
    <移行管理ID>/
      source.html          取得した旧ページ(一括処理)
      fetch.json           ページの台帳と「旧ページが変わった」の印(一括処理)
      changes.json         取り直しで見つけた変わった箇所(一括処理)
      candidates.json      本文、候補、確認の深さ、残る指摘(一括処理)
      decision.json        判断と確定した HTML(校正台)
  export/
    <取込回>/
      <移行管理ID>.html    FTP に上げる HTML(一括処理)
      url-map.csv          旧 URL と FTP 上の URL(一括処理)
  compare/
    <取込回>/<日時>/       比べ合わせの結果。取り込みの直後と 6-2 の2回を分けて置く(一括処理)
  logs/
    run-<日時>.jsonl       一括処理の実行の記録
```

書く部品を、ファイルごとに1つに決める(括弧の中が書く部品)。
同じファイルを2つの部品が書くことはない。
案件の設定だけは人と校正台の両方が書くので、変更履歴を残す。

10,000 ページでおよそ4万ファイルになる。
ローカルのディスクに置くので、共有ドライブの同期の遅さとアイテム数の上限は効かない(2026-10-08 の巡回で、共有ドライブに置くと続けられないと分かった。`trials/2026-10-08-crawl.md`)。
代わりに、ディレクターの PC のディスクの空きが要る。
候補のファイルは1ページ平均 47KB〜1.6MB で、1万ページで最大 16GB の見込みなので(`trials/2026-10-07-stage1.md`)、同時に最大6案件なら 100GB 近くになりうる。

### 共有ドライブに写すもの

共有ドライブには、案件ごとに受け渡しのフォルダを作り、次だけを置く(置くものは 2026-10-08 ユーザー確定。フォルダの形は案)。

```
<案件>/
  input/pages.json        GAS が書き出す入力。一括処理が案件のフォルダへ取り込む
  lists/                  一覧(巡回のページの一覧、コンテンツパターン、「AI 修正」タブへ写す status.csv など)
  export/<取込回>/        FTP に上げる HTML と url-map.csv
  evidence/<取込回>/      証跡(判断と確定した HTML)
```

写すのは一括処理の役目にし、校正台は共有ドライブを開かない。
証跡は、ページごとのファイルのままだと1万ファイルになり、共有ドライブで同じことが起きるおそれがあるので、取込回ごとに1つのファイルにまとめて写す案にする(形は段3で決める)。写す時期を「確定のたび」や「1日の終わり」にするなら、取込回より細かい単位でまとめることになるので、このフォルダの形は時期の決定に合わせて変える。

写すのは、一括処理の受け渡しのコマンド(案)にする。写したあとにファイルの数を照らし、写し終わりの印を置く。印の無い書き出しは FTP に上げない。
FTP に上げる HTML はページごとのファイルのままだが、数は取込回ごと(数百〜数千)で、1件も小さい。

## Claude Code の役割

Claude Code は、ディレクターの PC で一括処理のコマンドを動かし、結果の数を読んで、次に何をするかをディレクターに伝える。
修正の候補を作る AI は、さくらか Gemini で、Claude Code ではない。

旧サイトの本文を Anthropic に送らないために、次を守る。

- 一括処理のコマンドは、画面に件数、移行管理 ID、理由だけを出し、本文や HTML を出さない。`logs/` の実行の記録にも本文を書かない。
- Claude Code には、案件のフォルダの中身(`pages/`、`crawl/pages/`、`export/`、`compare/`、`logs/`)と、共有ドライブの受け渡しのフォルダの `export/` と `evidence/` を開かせない。案件のフォルダに置く Claude Code の指示ファイルと、読み取りを止める設定で縛る。
- ディレクターが Claude Code に頼めることを、手順書(スキル)にまとめる。取得、型のまとめ、本処理、再開、再処理、書き出し、確かめ、取り直し、比べ合わせ、指標の報告。

この縛りで足りるか、本文が Anthropic に届く経路がほかに無いかは、`goal2-app/LLM_DATA_POLICY.md` の見直しと合わせて確かめる。

## データの扱い

- 本文を AI(さくらか Gemini)に送ることは、1-1 の移行計画書で自治体の同意を確かめる(`FLOW.md`)。同意が取れない案件では、AI を呼ぶ候補(画像の代替テキストの下書きなど)を止め、ルールだけの候補で動かす。
- 旧ページ、候補、判断は、ディレクターの PC の案件のフォルダに置く。共有ドライブに写すのは、一覧、書き出し、証跡だけにする。案件の終わりに、PC の案件のフォルダ(旧ページの写しを含む)を消す。共有ドライブの受け渡しのフォルダをいつまで残すかは、今の運用の証跡と同じく、保存期間の決まりが無い。
- AI の鍵(さくらの API キー)や Google の認証は、PC の環境変数か gcloud の認証に置き、案件のフォルダにもこのリポジトリにも置かない。
- シートにある認証情報の類は、この仕組みのどのファイルにも写さない。GAS の書き出しは、ページの一覧のタブだけを読む。

## 決めてほしいこと

- 内部リンクの変換をいつ、どの範囲で確かめるか。変換のボタンは取込環境全体(ほかの人の行を含む)を対象に動き、別の取込環境でも同じである。取込環境を使う人と、押す時期を決める。
- FTP に上げて取り込んだあとに誤りが見つかったページの直し方。CMS の画面で直すのを基本にし、登録し直すときは、新しい移行管理 ID でも移行元 URL は元の FTP 上の URL を使う、先に作ったページの削除を移行業者に頼む、同じ移行元 URL の行が2つあるときの内部リンクの変換を試験で確かめる、を案にする。取込データには既存のページに差分を入れる列もあるので、同じ移行管理 ID で新しい内容を入れ直せるかも試験で確かめる。
- 「AI 修正」タブの列(上の案でよいか)。既存の「一覧」の列(証跡、移行完了日など)へ写すか。
- 却下の理由の選択肢(上の5つでよいか)。
- 確認不要に入れてよいルールの条件(そのまま採用が 99% 以上、害のある候補0件)と、抜き取りの割合でよいか。
- 承認に回す型の大きさの下限(10ページ)でよいか。
- 一括処理を Colab に移す場合に、Colab を業務で使ってよいか。
- 証跡を共有ドライブに写す時期(確定のたびか、1日の終わりか、取込回の書き出しのときか)。
- 受け渡しのコマンドを誰がいつ動かすか。案は、取得と本処理と書き出しの前に、共有ドライブの入力が案件のフォルダの入力より新しければ止まって知らせ、コマンドの終わりに一覧を写す形。取り込まずに古い入力のまま処理すると、シートの版が上がった分(足した行、外した行)が抜ける。
- ディレクターの PC のディスクの大きさ。同時に最大6案件で 100GB 近くになりうる(「案件のフォルダの形」)。案件のフォルダは1台の PC にしかないので、PC が壊れたときに判断を戻せるのは、共有ドライブに写した証跡だけである。
- `FLOW.md` の「決まっていないこと」のうち、取込回の取り込み日と、シートの版の引き継ぎ。

## 危ないところ

- 確認の時間: しっかり確認の割合が見込みより多いと、10,000 ページの案件は期間に収まらない(`FLOW.md` の日程の目安)。段 2 で割合を測り、収まらなければ、しっかり確認の候補の精度(表と見出し)を先に上げる。
- 型の数: 旧サイトのテンプレートが多いと、型の承認がディレクターの時間を食う。段 1 で型の数を数え、小さな型を汎用の判定に回す下限で調える。
- 共有ドライブ: 案件のフォルダを共有ドライブ(Drive for desktop)に置くと、ファイルの操作が1回0.25〜0.5秒かかり(手元のディスクは約0.002秒)、ページの写しを書き続けるとアイテム数の上限に達して、書き込みが返ってこなくなった(エラーの種類は `MOVED_TO_ROOT_TD_LIMIT_EXCEEDED`。共有ドライブのアイテム数の上限とみられる)。書いたはずの写しが残らないことと、同期の衝突とみられる状態のファイルの消失も起きた(2026-10-07〜08 の巡回。`trials/2026-10-08-crawl.md`)。そのため、案件のフォルダはローカルに置き、共有ドライブには受け渡すものだけを写す。写すものも、ページごとの小さなファイルが数万になると同じことが起きうるので、証跡は取込回ごとにまとめる案にする。
- 共有ドライブへの写しの失敗: 写す先は、巡回で止まったのと同じ Drive for desktop である。写しが途中で止まる、古い一覧を GAS が読む、書き出しの HTML が一部だけ写った状態で FTP に上げる、ことが起きうる。写したあとにファイルの数を照らし、写し終わりの印を置き、印の無いものは使わない。止まったら写し直す(試走で、ページの写しをローカルへ移したときと同じ考え方)。
- 案件のフォルダが1台の PC にしかない: PC が壊れたり、案件をほかのディレクターに渡したりすると、案件のフォルダを開けない。取り直せるのは旧ページと候補だけで、それも移行中に旧ページが変われば同じ本文にはならない。ディレクターの判断は、共有ドライブに写した証跡からしか戻せない。案件の設定(承認した型の範囲、一括の決定)、確定の索引、取り込みの日は写さないので戻せない。案件の設定も証跡と一緒に写すかは、写す時期と合わせて決める。証跡を写す時期(「決めてほしいこと」)と、証跡から判断を戻す手順を決める。
- 書きかけのファイル: 一括処理はページごとのファイルを裏で並べて書くので、途中で止まると書きかけのファイルが残り得る。同じページのフォルダでは旧ページを先に、台帳をあとに書き、書きかけの JSON は無いものとして読む。巡回は、写しが残らなかったページを再開のときに取り直す。
- File System Access API: Chrome の仕様と、会社の PC の制限(ブラウザの方針でファイルの書き込みを止めていないか)に頼る。段 3 の初めに、ディレクターの PC で確かめる。
- 旧サイトへの負荷と遮断: 一度に多く取ると、旧サイトの WAF に止められる。取得の間隔と同時数を案件の設定で絞り、取り直しは条件付きの取得にし、止められたページは取得できないとして記録する。取得素材ドメインを使うと、取り込みのたびに CMS も取込回の全ページの画像と PDF を旧サイトから取りに行くので、取り込みの最中に止められることもある。
- 取り込んだあとの直し: CMS は一度取得した HTML を取得し直さないので、取り込んだあとに見つけた誤りは、CMS の画面で直すか、登録し直すしかない。確定の前の確かめ(残る指摘、取り込みの事前の確かめ)で、上げる前に見つける。
- FTP 上の URL が公開ページに残る: 内部リンクに変わらなかったリンクは FTP 上の URL のまま公開される。書き換えを、部品に分ける案件の、リンクだけの段落のリンクに限る。本文のかたまりに残るリンクは旧 URL のまま書き出す。比べ合わせで FTP のサーバへのリンクを探す。
- 旧 URL のまま残る内部リンクが多い: 「そのまま」の設定では、文の中、箇条書き、表の中の内部リンクは旧 URL のまま公開側に残り、移行業者が CMS で直す。「リンクだけの段落」の判定を厳しくしている(本文の直下の `p` に限る)ので、本文を `div` で包んだ旧サイトでは、書き換えないリンクがさらに増える。比べ合わせで旧 URL のまま残った数を取込回ごとに数え、移行業者の作業量の見積もりに使う。
- 取り込みが止まる、長引く: 応答しないサーバへのリンクがあると、取り込みが長く止まり、画面から止められないことがある。素材1件ごとの取得の待ち時間も積み重なる。一括処理が前もって見つけて小さな取込回に分け、取込回の大きさを決めるときに素材の数も数える。
- CMS の取り込みの仕組みが変わる: 開発チームの協力が無いので、変わったことに気づきにくい。CMS 取込試験を、取込環境が新しくなるたびに回し、比べ合わせの崩れの数を取込回ごとに見る。
- 本文が Anthropic に届く: Claude Code に案件のフォルダを開かせない縛りが破られると、旧サイトの本文が届く。縛りの設定と、一括処理の出力に本文を出さないことの両方で防ぐ。
