# リニューアルの設計書

ディレクター1人が、1案件 1,000〜10,000 ページの旧サイトの本文を、取り込む前に1ページずつ確かめて直す仕組みの設計である。
業務の流れは `FLOW.md`、確認画面(校正台)の見た目と操作は `DESIGN.md` と `review-mockup.html` にあり、この文書はその2つを前提に、仕組みの部品、データの形、作る順番を決める。

CMS の取り込みに関わる節(「CMS に渡す HTML の約束」)は、2026-10-05 の CMS 取込試験の観察と、CMS の取り込みの振る舞いを調べた結果にもとづく。受け付けるタグの細部は、CMS 取込試験の結果で書き足す。

## 前提

2026-10-04〜05 にユーザーが決めたこと、確かめたことを前提にする。

- 利用者はディレクターだけで、案件ごとに1人。確認画面での確認に使えるのは1日5時間。移行業者と承認者は、この仕組みの画面を開かない。
- 規模は1案件 1,000〜10,000 ページ(「移行する」の数)、期間は約3か月、同時に最大6案件。
- すべてのページを目視で確かめる。そのぶん、自動で作る修正の候補の精度を上げる。
- 直した HTML の断片を共有ドライブに置き、ディレクターが FTP 領域に上げ、取込データの移行元 URL を FTP 上の URL に置き換えて、CMS に取り込ませる。
- CMS の取り込みについて確かめたこと(2026-10-05): HTML は断片のままでよい。画像と PDF は旧サイトの絶対 URL のままで取り込まれる。`#id` のページ内アンカーは残らない。受け付けるタグは CMS 取込試験(`docs/cms-import-tag-test/`)で確かめる。
- CMS の開発チームには、この仕組みのための変更を頼めない。
- 移行管理シートはディレクターが作る。GAS で書き戻してよい。
- ディレクターの PC は、ユーザーの PC とほぼ同じ構成で、ソフトを入れられる。Claude Code を「道具を動かす係」として使う。修正の候補を作る AI は、さくらか Gemini のまま。
- 手放してよいもの: npm 依存ゼロ、Windows 版 `.exe`、Cloud Run。残すもの: データベースを持たない。

## 目標と測り方

この仕組みの目標は、2つある。
一つは、ディレクターが1日5時間で、案件の「移行する」ページを期間内に確定できること。
もう一つは、取り込んだあとの移行業者の手直しと承認者の差し戻しを減らすことで、これは候補の精度で決まる。

候補の精度は、次の5つで測る。
どれも確認画面の操作と一括処理の出力から自動で数えられるので、ディレクターに記録の手間を増やさない。

| 指標 | 数え方 | 何が分かるか |
| --- | --- | --- |
| 採用率 | 出した候補のうち、ディレクターが採用(編集して採用を含む)した割合。ルール別、案件別 | 当たらないルール。採用率の低いルールは、条件を絞るか、案件の設定で切る |
| 見逃し | 確定した HTML のうち、ディレクターが候補を通さずに手で直した箇所 | 候補が足りないルール。共通のルールに足す材料 |
| 害のある候補 | 却下のうち、理由に「意味が変わる」「行政情報として不正確」を選んだもの | 自動で採用してはいけないルール。1件でも出たら、そのルールを確認不要の判定から外す |
| 残る指摘 | 確定した HTML に miChecker と同じ検査をかけ、本文に残った指摘の数 | 取り込む前に分かる品質。6-2 の本物の miChecker と突き合わせる |
| 取り込み後の手直し | 6-2 で数える、移行業者がさらに直した箇所と承認の差し戻し | この仕組みの最終の効き目 |

却下のときは、理由を1つ選ぶ(「意味が変わる」「行政情報として不正確」「案件の方針と違う」「直す必要がない」「その他」)。
キー1つで選べるようにし、確認の速さを落とさない。

## 全体の構成

部品は5つで、サーバーを持たない。

```
 移行管理シート(Google スプレッドシート)
   │ ① GAS のメニュー「一括処理の入力を書き出す」
   ▼
 共有ドライブ(Drive for desktop で PC に同期)
   案件のフォルダ ── 入力、ページごとの候補と判断、直した HTML、案件の設定、取込回の書き出し
   ▲ │                                     ▲ │
   │ ▼ ② 一括処理(ディレクターの PC の Node)  │ ▼ ③ 校正台(Chrome で開く静的 HTML)
   │      旧ページの取得、本文の抽出、候補、     │      ページを1枚ずつ確かめて確定
   │      安全な候補の採用、残る指摘、確認の深さ  │
   │                                          │
   │ ④ 一括処理「書き出し」: 確定したページの HTML と URL の対応表、状態の一覧
   ▼
 ⑤ GAS のメニュー「AI 修正を更新」「移行元 URL を置き換える」 → 移行管理シート
   ディレクターが取込回のフォルダを FTP 領域に上げる → CMS が取り込む
```

- ① と ⑤ の GAS は、シートに付けたメニューから、ディレクターが自分の権限で動かす。Web アプリとして公開しないので、PC から GAS を呼ぶための鍵や認証が要らない。
- ② と ④ は同じコマンドの別の動き(サブコマンド)で、ディレクターが Claude Code に頼んで動かす。
- ③ はファイルを開くだけで動く。サーバーも拡張機能も要らない。

この形を選んだ理由は3つある。
利用者がディレクター1人なので、複数の人の同時編集を受けるサーバーが要らない。
1案件 10,000 ページの一括処理は数時間かかる見込みで、ブラウザのタブで回すより、止まったところから再開できるコマンドの方が扱いやすい。
データベースを持たない前提でも、ページごとのファイルと案件ごとの集計ファイルで、必要な問い(残りの数、ルール別の採用率、同じ画像が何ページにあるか)に答えられる。

一括処理は、ディレクターの PC で長く動かせないとき(スリープ、ほかの作業との取り合い)のために、Google Colab でも動かせる形にしておく(Colab では Node と Playwright を入れ直す必要があり、実行時間の上限と切断もある)。
Colab に移すのは、試走で PC での運用が苦しいと分かったときだけにする。

## 一括処理

一括処理は Node のコマンドで、Playwright の Chromium の中で今のエンジン(`goal2Engine` と miChecker 互換エンジン)を動かす。
エンジンを Node 単体(jsdom など)に移さないのは、DOM の振る舞いの差で、miChecker 互換テスト(223 件)と出力テストをやり直すことになるため。
ブラウザのテストがすでに Playwright で動いているので、動かし方の実績もある。

### 入力

- GAS のメニュー ① が、シートの「移行する」行を、案件のフォルダの `input/pages.json` に書き出す。中身は移行管理 ID、旧 URL、ページタイトル、グループ、テンプレートの番号、取込回の番号(シートで指定したもの)。
- 案件の設定 `project/settings.json`(後述)。
- 共通のルール(`a11y-migration-kb/` から作る `rules.jsonl`)。一括処理に同梱する。

シートを直接読まずに書き出したファイルを読むのは、シートの版が上がったときに、どの版で処理したかを証跡に残すため。
書き出すとき、GAS はシートの名前と版、書き出した日時をファイルに入れる。

### 処理の段

ページごとに、次の段を順に行う。

1. 取得: 旧 URL からページ全体を取る。取れなかったら(404、タイムアウト、エラーのページ)理由を記録して次のページへ進む。取得した HTML は `pages/<移行管理ID>/source.html` に保存する。旧サイトが先に閉じても、確認と再処理ができるようにするため。あわせて、ページの台帳(後述)を書く。
2. 本文の抽出: ページを構造の型でまとめ、型ごとに承認した本文の範囲で抜き出す(後述の「構造の型と本文の範囲」)。どの型にも当たらないページと、抜き出せなかったページは、今の Goal 3 の汎用の判定で抜き出し、しっかり確認に回す。
3. 候補: 共通のルールと案件の設定で、修正の候補を作る。画像の代替テキストなど AI に頼む候補は、ここで、さくらか Gemini を呼ぶ。
4. 安全な候補の採用: 「確認不要に入れてよい」と決めたルールの候補だけを自動で採用する。構造を変える候補(表、見出し、リスト)は、決して自動で採用しない。
5. 残る指摘: 直したあとの HTML に miChecker 互換エンジンをかけ、本文に残る指摘を数える。
6. 取り込みの事前の確かめ: 取り込みで失敗する条件と止まる条件を調べる(「CMS に渡す HTML の約束」の「一括処理が前もって確かめること」)。
7. 確認の深さ: 次の節の決まりで、しっかり確認、さっと確認、確認不要に分ける。

結果は `pages/<移行管理ID>/candidates.json` に書く。
一括処理は、確認画面での判断(`decision.json`)を決して書き換えない。

### ページの台帳

一括処理は、取得したページごとに、次の項目を `pages/<移行管理ID>/candidates.json` の「台帳」の部分に書き、`project/summary.json` にも集める。
旧サイトを、移行管理シートの行と1対1で突き合わせられる台帳に変えておき、取得できない理由、取り込みで失敗する理由、移行中の更新を、同じ台帳の上で数えるため。

- 移行管理 ID、旧 URL、取得の日時、HTTP の状態、最終の URL(転送のあと)。
- 本文のハッシュ(本文の文字を整えてから計算する)と、構造のハッシュ(次の節)。
- 構造の型、本文の範囲をどう決めたか(型の範囲か、汎用の判定か)。
- 本文にある画像、PDF などのファイル、外部のリンクの一覧と数。
- 対象外の理由(取得できない、本文が空、など)。

### 構造の型と本文の範囲

同じテンプレートのページは、本文の範囲も同じ場所にあることが多い。
一括処理は、ページの DOM から文字を除き、要素の名前と ID とクラスの並びを整えてハッシュにし(構造のハッシュ)、同じハッシュのページを1つの「構造の型」にまとめる。
本文の部分は、ページごとに長さも中身も違うので、ハッシュに入れるのは本文の範囲の外側(ヘッダー、ナビゲーション、本文を囲む要素まで)にとどめる。

型ごとに代表のページを1つ選び、ディレクターが校正台で本文の範囲を承認する。
承認した範囲は案件の設定に型ごとに入り、同じ型のページに使い回す。
シートのテンプレートの番号は、型をまとめる手がかりに使い、型と番号が食い違うページは知らせる。

承認の前に、型ごとの範囲で抜き出した本文と、汎用の判定で抜き出した本文を並べて比べ(試しに両方を動かして結果だけを比べる)、食い違うページの数を型ごとに出す。
食い違いが多い型は、範囲を見直してから承認する。
承認したあとも、型の範囲で抜き出せなかったページ、構造のハッシュがどの型にも当たらないページは、汎用の判定に戻して、しっかり確認に回す。

### 再開と再処理

- 再開: `candidates.json` があるページは飛ばす。止まったら、同じコマンドをもう一度動かせばよい。
- 再処理: 案件の設定や共通のルールが変わったとき、まだ確定していないページだけを処理し直す。候補には、箇所とルールから作る変わらない鍵を持たせる。判断の引き継ぎは、校正台が `decision.json` の判断と新しい候補を鍵で突き合わせて行い、一括処理は `decision.json` を書かない。確定済みのページには遡らない(`FLOW.md` の 3-4)。
- 取り直し: 旧サイトが移行中に更新されたときのために、旧 URL を取り直すサブコマンドを置く。本文のハッシュを台帳の値と比べ、差があるページについて、日付、金額、連絡先、期限の変わった箇所を抜き出す。差の扱いは、ページの状態で分ける。
  - まだ確定していないページは、新しい本文で処理し直す。
  - 確定したが FTP に上げていないページは、確定を外して待ち行列に戻し、変わった箇所を指示として見せる。
  - 取り込み済みのページは、変わった箇所の一覧を、6-1 の移行業者に渡す(CMS は同じ移行管理 ID で HTML を取得し直さないため)。
- 取り直しは、取込回ごとの書き出しの直前と、旧サイトの更新が多い案件では週に1回、回す。

### 速さの見込み

10,000 ページで、取得に1ページ1〜2秒(旧サイトに負荷をかけないよう、同時に取るのは2ページまで)、エンジンに1ページ1秒前後、AI の呼び出しは画像の数による。
取得とエンジンだけなら数時間、AI を含めると半日から1日になる見込みで、これは推測なので試走で測る。
旧サイトへの取得の間隔と同時数は、案件の設定で変えられるようにする。

## 確認の深さの決め方

一括処理は、ページごとに確認の深さを1つ決める。
決め方は、そのページの候補のうち一番重いもので決まる。

| 確認の深さ | 入る条件 | ディレクターがすること |
| --- | --- | --- |
| しっかり確認 | 構造を変える候補(表、見出し、リスト)、意味に関わる候補(本文の言い換え、代替テキストの新規作成)、「確かめる点あり」の候補、本文の抽出の失敗、取り込みの事前の確かめに引っかかった | 修正前と修正後を読んで判断する |
| さっと確認 | 表記の揃え、既存の代替テキストの手直し、リンクの文言の補正など、小さな直しだけ | 差分を見て採用する |
| 確認不要 | 候補が無い、または確認不要に入れてよいルールの候補だけ | 開かない |

確認不要に入れてよいルールは、初めは空にし、次の条件を満たしたルールだけを足す。

- 試走と取込回で、そのまま採用した割合が 99% 以上(編集して採用は数えない。却下と編集が100件に1件以下)。
- 害のある候補が0件。
- ルールの性質として、意味を変えない(全角英数字を半角にする、など)。

ルールを確認不要に入れるか外すかは、案件の設定で案件ごとに決め、共通のルールの側では「入れてよい候補」の印だけを持つ。
害のある候補が1件出たら、一括処理は `project/metrics.json` に「確認不要から外すべきルール」として書き、次の処理からそのルールの自動の採用を止める。外すことの確定は、校正台でディレクターが行い、校正台が案件の設定を書き換える。一括処理は案件の設定を書かない。

確認不要のページは開かれないので、確認不要に入れたルールの害は、そのままでは見つからない。
そこで、確認不要のページのうち一部(たとえば50ページに1ページ)を抜き取って、さっと確認に回す。
6-2 で数える取り込み後の手直しも、確認不要に入れたルールの見張りに使う。

## 校正台

校正台は、`review-mockup.html` を本物のデータで動くようにしたものである。
見た目と操作は `DESIGN.md` に従う。

### ファイルの読み書き

Chrome の File System Access API で、PC に同期された共有ドライブの案件のフォルダを開く。
初めに一度フォルダを選べば、次からはブラウザが選んだフォルダを覚えている(許可の確認は出る)。

- 読む: `input/pages.json`、`pages/*/candidates.json`、`pages/*/decision.json`、`project/settings.json`、`project/summary.json`、`project/metrics.json`。
- 書く: `pages/<移行管理ID>/decision.json`、`project/review-index.json`、案件で採用したルールの決定(`project/settings.json` の該当部分)。

採用、却下、確定のたびに、その場で書く。
「保存」のボタンは置かない。

10,000 ページ分のファイルを開くたびに読むと遅いので、一覧に要る項目は一括処理が `project/summary.json` にまとめ、校正台はまずそれだけを読む。
確定の状態は `decision.json` にあり、`summary.json` には入らないので、校正台は自分だけが書く索引 `project/review-index.json`(ページごとの状態と確定日)を持ち、判断のたびに書き足す。
ページの中身は、そのページを開いたときに読む。

Drive for desktop の同期のしかた(ストリーミングかミラーか)で、読み書きの速さが変わる。
ストリーミングでは、開いたことのないファイルの読み込みにネットワークを待つので、案件のフォルダは「オフラインで使用可能」にするか、ミラーにする。
どちらが要るかは、試走で測る。

校正台は `file://` で開く前提なので、選んだフォルダを覚える仕組みと許可の確かめが Chrome で期待どおりに働くかを、段 3 の初めに確かめる。
書体は、校正台の HTML と同じフォルダに置いて読み込む(`DESIGN.md` の「自分のサーバーに置く」は、この形に読み替える)。

### 判断の記録

`decision.json` には、候補ごとの判断(採用、編集して採用、却下とその理由、後回しと質問の下書き)、ページの確定の時刻、確定した HTML、ディレクターが手で直した箇所の差分を書く。
今の証跡の形(候補、判断、修正前後、理由、関連する WCAG)を引き継ぎ、6-2 や顧客への説明に使えるようにする。

### 一括の決定

右の列の指示から「このルールを案件の全ページで採用」を押すと、校正台は案件の設定にその決定を書く。
まだ開いていないページのファイルは書き換えず、ページを開いたときに案件の設定から「案件で採用」と表示する。
画像の代替テキストも同じで、同じ画像の URL が案件のほかのページにあれば、決めた代替テキストを使う。
この一括の決定は、確定済みのページには効かない。
自治体の方針に関わる決定は、ここでは決めず、自治体に確かめる(`FLOW.md` の 3-4)。

## 案件の設定

案件の設定は `project/settings.json` の1つのファイルで、共通のルールの上に重ねる。
共通のルールそのものは書き換えない。

- 本文のセレクタ: テンプレートの番号ごと。
- 表記の決まり: 日付、電話番号、単位など、自治体ごとの書き方。
- ルールごとの扱い: 自動で採用(確認不要に入れる)、確認する、使わない。
- 辞書: 画像の URL と代替テキストの対応、同じ表記の置き換え。
- 取り込みの決まり: 強制アクセシビリティチェックに当たる文字、禁則文字の変換(5-4 と揃える)。
- 取得の決まり: 旧サイトへの取得の間隔と同時数、除く URL。

変更は履歴を残す(変更した日時、誰が、どの画面から)。
案件の設定で繰り返し出る決まりは、ユーザーが既存のトリアージの手順で共通のルールに足す。

## シートへの書き戻し

シートへの書き戻しは、GAS のメニューで行う。
PC から GAS を呼ばないので、鍵や認証の置き場が要らない。

- 「一括処理の入力を書き出す」: 「移行する」行を `input/pages.json` に書き出す(前述)。
- 「AI 修正を更新」: 一括処理が書いた `project/status.csv`(移行管理 ID ごとの状態の一覧)を読み、「AI 修正」タブに写す。10,000 行でも1つのファイルなので、GAS の実行時間の上限(6分)に収まる。
- 「移行元 URL を置き換える」: 一括処理が書いた取込回の `url-map.csv`(移行管理 ID、旧 URL、FTP 上の URL)を読み、取込データの移行元 URL を置き換える。置き換える前の値は別の列に残し、戻せるようにする。

「AI 修正」タブの列は、次を案にする。
既存の「一覧」の列には書き込まない。

| 列 | 中身 |
| --- | --- |
| 移行管理 ID | 「一覧」と突き合わせる鍵 |
| 取込回 | 書き出した取込回の番号 |
| 確認の深さ | しっかり確認、さっと確認、確認不要 |
| 状態 | 未処理、取得できない、未確認、後回し、確定、書き出し済み |
| 取り込めない理由 | ページタイトルが60字以上、グループが空欄、取得できない、など |
| 指示の数、採用、却下 | 件数 |
| 残る指摘 | 確定した HTML の本文に残る指摘の数 |
| 質問の下書き | 後回しの指示に付けた下書き |
| 旧 URL、FTP 上の URL | 対応 |
| 確定日 | 校正台で確定した日 |
| 証跡の場所 | 案件のフォルダの中のページのフォルダ |

## 書き出しと FTP

取込回の書き出しは、一括処理のサブコマンドで行う。

1. 指定した取込回の、確定したページを集める。後回しの指示が残るページは外す。
2. 確定した HTML を `export/<取込回>/<移行管理ID>.html` に書く。文字コードとファイルの形は、CMS が取り込める形にする(次の節)。案件の取り込みの設定で「部品に分ける」が有効なときだけ、本文の中の「移行するページへのリンク」を、そのページの FTP 上の URL に書き換える(次の節の「リンク」)。画像と PDF を FTP に写す案(次の節の案 B)を選んだときは、それらも写し、本文の URL を書き換える。素材の FTP 上の URL も取込回によらず、旧 URL から一つに決まる形にする(旧 URL のパスを半角英数字と `-` `_` に整えて使う)。同じ画像が別の取込回のページに出ても、CMS が同じ素材として扱えるようにするため。
3. `export/<取込回>/url-map.csv` を書く。FTP 上の URL は、案件の設定の FTP の URL の頭に移行管理 ID をつないで作り、取込回を含めない。後の取込回で取り込むページへのリンクを、先に書き換えておけるようにするため。
4. 校正台の `review-index.json` を読んで、`project/status.csv` を書き直す。

ディレクターは、`export/<取込回>/` の中身を、FTP 領域の案件のフォルダ(取込回で分けない)に上げ、シートのメニューで移行元 URL を置き換える。
CMS は一度取得した HTML を取得し直さないので、同じ移行管理 ID のファイルを上げ直しても取り込みには効かない。
FTP に上げる作業を一括処理から行わないのは、FTP の接続先と認証を PC の外に置きたくない(ディレクターの FTP の道具に任せる)ため。
上げたファイルが FTP 上の URL で取れることは、一括処理の「確かめ」のサブコマンドで、URL を順に取って確かめる。

## CMS に渡す HTML の約束

この節は、2026-10-05 の CMS 取込試験の観察と、CMS の取り込みの振る舞いを調べた結果(非公開のメモ)にもとづく。
調べでわかったことのうち、取込試験でまだ確かめていないものには「試験で確かめる」と書いた。
取り込みの振る舞いは、案件ごとの取り込みの設定(本文の範囲、部品に分けるかどうか、文中のリンクと画像を外に出すかどうか、別のサーバの素材を取り込むかどうか)で変わるので、案件の設定に、その案件の取り込みの設定を写しておく。

### 取り込みの進み方

- 取り込みは、担当者が CMS の画面のボタンで始める。日時を指定して自動で動く仕組みは無い。`FLOW.md` の「取り込み日」は、運用で決める予定日である。
- CMS は、取り込みの最初の段階で移行元 URL の HTML を取得し、同じ移行管理 ID では取得し直さない。取得した時点で HTML が決まるので、そのあと FTP 上の HTML を直して置き直しても反映されない。だから、FTP に上げるのは確定したページだけにし、上げたあとの直しは CMS の画面で行う。
- 4-1 の取り込みテストで、本番と同じ取込環境に同じ移行管理 ID でページを登録すると、その行は旧サイトの HTML のまま決まってしまう。取り込みテストと本番とで、取込環境か移行管理 ID を分ける。
- 取り込みは、本文のリンク先に実際に接続しに行く。応答しないサーバへのリンクがあると、取り込みが長く止まる。
- 取り込み結果の一覧には、成功した行にも注意が書かれる。

### HTML の形

- HTML の断片のままでよい(取込試験で確認)。ファイルの先頭で文字コードを宣言する(宣言が無いと UTF-8 として読まれる見込み。試験で確かめる)。
- FTP 上の URL は、半角英数字と一般的な記号だけで書き、サーバ名の後に必ずパスを付ける。移行管理 ID もこの文字だけで作る。
- 本文は、案件で決めた本文の範囲(決まった ID やクラスの要素)で囲む。範囲が見つからないと、ファイル全体が取り込まれる。
- `id`、`class`、`style`、`lang`、`role`、`aria-*` は取り込みで消える(`role` と `aria-*` 以外は試験で確かめる)。意味を色や位置や属性だけで伝えない。外国語の `lang` のように CMS で付け直す必要があるものは、ページごとに一覧にして、6-1 の移行業者に渡す(試験で確かめる)。
- `h1` は中身ごと消える。本文の見出しは `h2` から始め、レベルを飛ばさない。`h2` が無いと、見出し全体が1段ずつ繰り上がる。
- 取り込みの設定によっては、`p`、`div`、`span` のタグが外れる。段落の区切りがどう残るかは、試験で確かめる。
- `script`、`style`、`form`、`iframe`、`svg`、`hr`、`figure` などは、消えるか文字だけが残る。入れない。
- `b`、`i`、`u`、`strike`、`small` は取り込みでは残るが、CMS の公開前のチェックで止まる。`strong`、`em` を使う。
- 本文中の `&lt;` `&gt;` は、取り込みで文字に戻ったあとタグとして読まれることがある。一括処理は、本文に `<` `>` を文字として含むページを「確かめる点あり」にする。
- ルビ(`ruby`)は使わず、括弧書きにする。
- `#id` のページ内アンカーは残らない(取込試験で確認)。共通のルール「ページ内アンカーリンク」に沿って、文章で示す形に直す。
- 電話番号へのリンク(`tel:`)は消える。番号は文字として書く。

### 画像とファイル

- CMS は、移行元 URL と同じサーバにある画像とファイルだけを、CMS の素材として取り込む。移行元 URL を FTP 上の URL に置き換えると、旧サイトの画像と PDF は「別のサーバ」になり、素材にならずに旧サイトの絶対 URL のまま残る(取込試験の観察と一致する)。別のサーバの素材を取り込む設定もあるが、効き方は試験で確かめる。
- 素材にならなかった画像と PDF は、旧サイトが閉じると切れる。
- 画像は JPEG、PNG、GIF にする。SVG は取り込みに失敗し、設定によってはそのページ全体が登録されない。WebP と `data:` の埋め込み画像も避ける(SVG と WebP の振る舞いは試験で確かめる)。
- 取得できない画像があると、設定によってはそのページ全体が登録されない。取得できないファイルは、エラーとして報告されずに空のファイルとして登録されることがある(試験で確かめる)。
- ファイルの URL は拡張子で終わらせ、クエリ文字列を付けない。
- 画像の代替テキストが空のまま部品に分けられると、本文に仮の記号が入る。

画像と PDF の扱いは、次の2つの案から選ぶ(「決めてほしいこと」)。

| 案 | すること | 良いところ | 困るところ |
| --- | --- | --- | --- |
| A. 旧サイトの URL のまま | 何もしない(今の観察どおり) | 一括処理と FTP の作業が増えない | 素材にならない。旧サイトが閉じると切れる。移行業者が CMS で素材に登録し直す手間が残る(今の運用を確かめる) |
| B. FTP に写して素材にする | 一括処理が画像と PDF を取得して `export/` に写し、本文の URL を FTP 上の URL に書き換える。ディレクターが HTML と一緒に FTP に上げる | 移行元 URL と同じサーバになるので、CMS の素材として取り込まれる。旧サイトの終わりと切り離せる。一括処理が全件の取得を確かめられる | FTP に上げる量が増える(PDF が多い案件)。ファイル名は CMS の設定で乱数になることがある |

案 B を推す。
旧サイトの公開が終わる日に縛られなくなり、取得できない画像とファイルを取り込む前に全件見つけられるため。
案 B を選ぶ前に、取込試験で、FTP に置いた画像と PDF が素材になることを確かめる。

### リンク

- CMS は、本文のリンクがほかの行の移行元 URL と一字一句同じ(`http` と `https`、末尾の `/`、`index.html` の有無まで)で、その行の取り込みが済んでいるときだけ、リンクを CMS の内部リンクに変える。変換は、取り込みのあとに別のボタンで行い、部品に分ける設定のときだけ働く。
- 移行元 URL を FTP 上の URL に置き換えると、本文に残った旧 URL のリンクは、どの行の移行元 URL とも一致しなくなり、内部リンクに変わらない。
- そこで一括処理は、案件の取り込みの設定で「部品に分ける」が有効なときだけ、書き出すときに、本文の中の「移行するページへのリンク」を、そのページの FTP 上の URL に書き換える。他のページの見出しへのリンク(`#` 付き)は、`#` 以降を落として書き換える(`#` 以降も一致の対象になるため)。FTP 上の URL は、取込回によらず移行管理 ID だけで決まる形にする(「書き出しと FTP」の節)。後の取込回で取り込むページへのリンクも、取り込みが済んだあとに変換のボタンをもう一度押せば変わる。
- 「部品に分ける」が無効な案件では書き換えず、旧 URL のまま残す。FTP は一時的な置き場なので、FTP 上の URL が公開ページに残ると旧 URL より悪い。旧 URL のままなら、6-2 の「内部リンクが外部リンクのまま残っていないか」のチェックで見つかる。
- 変換されたあとも、部品に分けられずに本文のかたまりの中に残ったリンクは、元の URL のままになることがある(試験で確かめる)。6-2 で、公開ページに FTP のサーバへのリンクが残っていないかを確かめる。
- 移行しないページへのリンクと、外部のリンクは書き換えない。応答しないサーバへのリンクは、一括処理が前もって見つけて「AI 修正」タブに書く(下)。

### 一括処理が前もって確かめること

取り込みで失敗する条件と止まる条件を、一括処理の「取り込みの事前の確かめ」(処理の段 6)で調べ、ページの理由として記録する。

- ページタイトルが60字以上、機種依存文字や禁則文字を含む(その行は登録されない)。グループが空欄。
- 取得できない画像とファイル、SVG、WebP、`data:` の画像、クエリ付きのファイル URL。
- 応答しない、または応答の遅いサーバへのリンク(短い時間で区切って接続を試す)。該当するページは、まとめて小さな取込回に入れるか、取り込み担当者に知らせる。
- 本文に文字としての `<` `>` を含む。
- `h1` がある、`h2` が無い、見出しのレベルが飛ぶ。
- CMS の公開前のチェックで止まる表記(「TEL」「FAX」などの略記、日付の区切り、全角英数字、`b` `i` `u` など)。どの項目で止まるかは顧客ごとの設定なので、案件の設定に、その顧客で有効な項目を写す(5-4 と揃える)。

## 案件のフォルダの形

共有ドライブに、案件ごとに次のフォルダを作る。

```
<案件>/
  input/
    pages.json            GAS が書き出す「移行する」行と、シートの名前、版、日時
  project/
    settings.json         案件の設定(校正台と人が書く)
    settings-history.jsonl 案件の設定の変更履歴
    summary.json          一覧に要る項目の集計(一括処理が作る)
    status.csv            「AI 修正」タブへ写す一覧(一括処理が作る)
    metrics.json          精度の指標と、確認不要から外すべきルール(一括処理が作る)
    review-index.json     ページごとの確定の状態と確定日(校正台が書く)
  pages/
    <移行管理ID>/
      source.html         取得した旧ページ
      candidates.json     台帳、本文、候補、確認の深さ、残る指摘(一括処理が書く)
      decision.json       判断と確定した HTML(校正台が書く)
  export/
    <取込回>/
      <移行管理ID>.html   FTP に上げる HTML
      url-map.csv         旧 URL と FTP 上の URL
  logs/
    run-<日時>.jsonl      一括処理の実行の記録
```

書く部品を、ファイルごとに1つに決める。
一括処理は `candidates.json` と集計(`summary.json`、`status.csv`、`metrics.json`)を、校正台は `decision.json`、`review-index.json`、案件の設定を書き、同じファイルを2つの部品が書くことはない。
案件の設定だけは人と校正台の両方が書くので、変更履歴を残す。

10,000 ページでおよそ3万ファイルになる。
Drive for desktop の同期がこの数に耐えるかは、試走で確かめる。
耐えないときは、取込回ごとに1つのファイルにまとめる形に変える。

## 取り込み後の比べ合わせ

6-2 の移行後チェックで、CMS に取り込んだページを取り直し、旧ページ、確定した HTML、取り込んだあとのページの3つを比べる。
取り込みの振る舞い(「CMS に渡す HTML の約束」)で崩れる箇所を、目視の抜き取りでなく、全ページの数で見つけるため。

- 本文: 確定した HTML と取り込んだあとの本文の文字の差。消えた段落や、繰り上がった見出しを見つける。
- 画像と PDF: CMS の素材になったか、旧サイトの URL のまま残ったか。素材のファイルの大きさが0でないか。
- リンク: 内部リンクに変わったか、旧 URL や FTP のサーバへのリンクが残っていないか。
- ページ内アンカー: 確定した HTML で文章に直した箇所が残っているか。

比べる先のページの URL は、CMS の取り込み結果の一覧から取る。
プレビューの URL にログインが要るときの取り方(ディレクターが自分で開いたブラウザを使うかなど)は、段 6 の前に確かめる。
ログインの情報を、一括処理と Claude Code に渡さない。

旧サイトと CMS からの取得は、どれも同じ取得の部品で行う。
取りに行ってよいサーバを案件の設定で限り(旧サイトと CMS と FTP のサーバだけ)、取得の間隔と同時数、1ページの大きさの上限、やり直しの回数、止めたところからの再開を決めておく。
今の URL 取得の API にある、内部のネットワークのアドレスを取りに行かせない守り(SSRF 対策)も引き継ぐ。
CMS の取込環境が社内のネットワークのアドレスにあるときは、案件の設定で名前を挙げたサーバだけを、この守りの例外にする。
ブラウザでの描画(Playwright)を使うのは、JavaScript で本文を描くページだけにする。

## 採らないもの

- AI の呼び出しの履歴を圧縮する仕組み: 修正の候補を作る AI の呼び出しは、ページごと、候補ごとに独立した1往復で、圧縮する履歴が無い。
- AI による確認の深さの決定とルールの省略: 共通のルールは、すべてのページに決まった手順でかける。AI で型を分ける、レビューの順番を決めるといった補助を足すとしても、表示の順番を決める範囲にとどめ、本文を外部のサービスに送らずに、構造の特徴だけで試す。

## Claude Code の役割

Claude Code は、ディレクターの PC で一括処理のコマンドを動かし、結果の数を読んで、次に何をするかをディレクターに伝える。
修正の候補を作る AI は、さくらか Gemini で、Claude Code ではない。

旧サイトの本文を Anthropic に送らないために、次を守る。

- 一括処理のコマンドは、画面に件数、移行管理 ID、理由だけを出し、本文や HTML を出さない。`logs/` の実行の記録にも本文を書かない。
- Claude Code には、案件のフォルダの中身(`source.html`、`candidates.json`、`decision.json`、`export/`、`logs/`)を開かせない。案件のフォルダに置く Claude Code の指示ファイルと、読み取りを止める設定で縛る。
- ディレクターが Claude Code に頼めることを、手順書(スキル)にまとめる。一括処理、再開、再処理、書き出し、確かめ、指標の報告。

この縛りで足りるか、本文が Anthropic に届く経路がほかに無いかは、`goal2-app/LLM_DATA_POLICY.md` の見直しと合わせて確かめる。

## データの扱い

- 本文を AI(さくらか Gemini)に送ることは、1-1 の移行計画書で自治体の同意を確かめる(`FLOW.md`)。同意が取れない案件では、AI を呼ぶ候補(画像の代替テキストの下書きなど)を止め、ルールだけの候補で動かす。
- 旧ページ、候補、判断は、案件の共有ドライブにだけ置く。PC に残るのは同期の写しで、案件の終わりに同期を外す。
- AI の鍵(さくらの API キー)や Google の認証は、PC の環境変数か gcloud の認証に置き、案件のフォルダにもこのリポジトリにも置かない。
- シートにある認証情報の類は、この仕組みのどのファイルにも写さない。GAS の書き出しは、ページの一覧のタブだけを読む。

## 作る順番

試走で数字を取りながら進める。
各段の終わりに、その段で決めることを書いた。

1. エンジンの切り出しと一括処理の骨組み。`goal2Engine` を Playwright の中で動かすコマンドを作り、佐賀市の 51 ページと遠野市から抜いたページで、取得(ページの台帳を含む)、抽出、候補、残る指摘までを回す。構造のハッシュで型をまとめ、型ごとの範囲と汎用の判定を並べて比べる。今のテスト(出力、互換、表のネスト)が通ることを確かめる。決めること: 取得と処理の速さ、Drive for desktop の同期のしかた。
2. 確認の深さと指標。確認の深さの決め方と、精度の指標の数え方を入れる。遠野市の規模で回し、深さごとの割合を出す。決めること: 日程の目安(`FLOW.md`)の割合を実測に置き換え、10,000 ページの案件が期間に収まるか。
3. 校正台。`review-mockup.html` を本物のデータで動くようにする。File System Access API での読み書き、判断の記録、一括の決定、却下の理由。決めること: 1ページあたりの確認の時間の実測。
4. GAS のメニュー。入力の書き出し、「AI 修正」タブの更新、移行元 URL の置き換え。
5. CMS に渡す形と書き出し。取り込みの仕組みの調べと CMS 取込試験の結果で、HTML の約束と取り込みの事前の確かめを決め、書き出しと FTP 上の確かめを作る。CMS の取込環境に1取込回を取り込んで確かめる。
6. 取り込み後の比べ合わせと、1案件での試走。取り込み後の比べ合わせを作り、実際の案件の1取込回を、この仕組みで最初から最後まで回す。6-2 で、取り込み後の手直しと差し戻しを、今のやり方の案件と比べる。

段 1 と段 5 の調べは並べて進められる。
段 3 は、段 1 の出力の形が決まれば、段 2 と並べて進められる。

## 確かめ方

- 今のテスト(`npm test`、出力、互換、表のネスト、AI の呼び出し)を、エンジンを切り出したあとも通す。
- 一括処理の出力を、佐賀市の old と gold の比較器で、今の Goal 2 の画面の出力と比べ、悪くなっていないことを確かめる。
- 校正台は、Playwright で、キーだけの操作とマウスだけの操作の両方で、確定までを通す(モックアップと同じ確かめ方)。
- 書き出した HTML は、CMS 取込試験と同じ確かめ方(印を付けた HTML を取り込み、取り込み後と比べる)で、取込環境に入ることを確かめる。

## 決めてほしいこと

- 画像と PDF の扱い(「CMS に渡す HTML の約束」の案 A か案 B)。今、移行業者が旧サイトの画像と PDF を CMS の素材に登録し直しているか。
- 案件の取り込みの設定(部品に分けるかどうか、文中のリンクと画像を外に出すかどうか、別のサーバの素材を取り込むかどうか)を、誰がいつ決め、案件の設定に写すか。
- FTP に上げたあとに誤りが見つかったページの登録し直しの手順。移行管理 ID を変えると FTP 上の URL が変わり、ほかのページから書き換えたリンクと合わなくなる。新しい ID でも移行元 URL は元の FTP 上の URL を使う、先に作ったページの削除を移行業者に頼む、同じ移行元 URL の行が2つあるときの内部リンクの変換を試験で確かめる、を案にする。
- 「AI 修正」タブの列(上の案でよいか)。既存の「一覧」の列(証跡、移行完了日など)へ写すか。
- 却下の理由の選択肢(上の5つでよいか)。
- 確認不要に入れてよいルールの条件(採用率 99% 以上、害のある候補0件)でよいか。
- 案件のフォルダを、ディレクターの PC にミラーで同期してよいか(共有ドライブの運用の決まり)。
- 一括処理を Colab に移す場合に、Colab を業務で使ってよいか。
- `FLOW.md` の「決まっていないこと」のうち、取込回の取り込み日、シートの版の引き継ぎ、旧サイトの公開が終わる日。

## 危ないところ

- 確認の時間: しっかり確認の割合が見込みより多いと、10,000 ページの案件は期間に収まらない(`FLOW.md` の日程の目安)。段 2 で割合を測り、収まらなければ、しっかり確認の候補の精度(表と見出し)を先に上げる。
- 共有ドライブの同期: 1案件3万ファイルの読み書きが遅い、同期の衝突が起きる。段 1 で測り、だめなら取込回ごとのまとまったファイルにする。
- File System Access API: Chrome の仕様と、会社の PC の制限(ブラウザの方針でファイルの書き込みを止めていないか)に頼る。段 3 の初めに、ディレクターの PC で確かめる。
- 旧サイトへの負荷と遮断: 一度に多く取ると、旧サイトの WAF に止められる。取得の間隔と同時数を案件の設定で絞り、止められたページは取得できないとして記録する。
- 取り込んだあとの直し: CMS は一度取得した HTML を取得し直さないので、FTP に上げたあとに見つけた誤りは、CMS の画面で直すか、登録し直すしかない(登録し直しの手順は「決めてほしいこと」)。確定の前の確かめ(残る指摘、取り込みの事前の確かめ)で、上げる前に見つける。
- FTP 上の URL が公開ページに残る: 内部リンクに変わらなかったリンクは FTP 上の URL のまま公開される。書き換えを「部品に分ける」案件に限り、6-2 で FTP のサーバへのリンクを探す。
- 取り込みが止まる: 応答しないサーバへのリンクがあると、取り込みが長く止まり、画面から止められないことがある。一括処理が前もって見つけ、小さな取込回に分ける。
- CMS の取り込みの仕組みが変わる: 開発チームの協力が無いので、変わったことに気づきにくい。CMS 取込試験を、取込環境が新しくなるたびに回す。
- 本文が Anthropic に届く: Claude Code に案件のフォルダを開かせない縛りが破られると、旧サイトの本文が届く。縛りの設定と、一括処理の出力に本文を出さないことの両方で防ぐ。
