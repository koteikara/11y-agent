# 段1の試走(2026-10-07)

リニューアルの「作る順番」の段1として、一括処理の骨組み(`goal2-app/batch/`)を、6つの自治体の旧サイトで動かした記録である。
段1で決めることにしていた、取得と処理の速さ、型の数、共有ドライブの同期を測った。

## 試走の条件

- 対象:遠野市の移行管理シートの「移行する」1,922ページから、均等に抜き出した100ページ。ほかに、作りの違う5市(安城市、浦添市、弘前市、福山市、豊橋市)のシートにあった50〜52ページずつ。合わせて352ページ。
- 置き場所:案件のフォルダを共有ドライブ(Drive for desktop で同期)の試走用のフォルダに置いた。
- 取得:旧サイトへは1秒の間隔で、同時に2ページまで。
- AI:呼ばない設定(`ai.enabled: false`)。AI に頼む候補は、ルールだけの候補になる。
- 自動で採用にしたルール:無し(設計どおり、初めは空)。
- 型の承認:型のまとめが出した案を、そのまま承認したものとして本処理を回した。

## 結果

### 取得

| サイト | ページ | 取得できた | 取得できない |
| --- | --- | --- | --- |
| 遠野市 | 100 | 97 | 3(HTTP のエラー) |
| 安城市 | 50 | 48 | 2(HTTP のエラー) |
| 浦添市 | 50 | 50 | 0 |
| 弘前市 | 50 | 50 | 0 |
| 福山市 | 52 | 52 | 0 |
| 豊橋市 | 50 | 42 | 8(HTTP のエラー) |

遠野市の100ページの取得は約2分だった。
1万ページなら、同じ間隔で約3時間半になる見込みである。

取得が終わってもプロセスが閉じない不具合が見つかった。
読まなかった応答(404 など)の本文が、接続を握ったままになっていた。
読まない応答の本文を捨てるように直した。

### 型のまとめ

初めの作り(構造が完全に同じページをまとめる)では、遠野市の97ページが29の構造に割れ、承認に回せる型は2つだけだった。
原因は3つあった。

- メニューで今いる項目のクラス名が変わる(`globalPrimaryMenuSelected` など)。
- 一部のページだけにある部品がある。
- 左のメニューの開き方がページごとに違う。

構造を「要素の道」の集まりで表し、重なりが 0.8 以上なら同じ型とする形に変えた(`ARCHITECTURE.md` の「構造の型と本文の範囲」)。
変えたあとの結果は次のとおり。

| サイト | 型(10ページ以上) | 汎用の判定に回すページ | 範囲の案 |
| --- | --- | --- | --- |
| 遠野市 | 1(97ページ) | 0 | `#CenterArea` |
| 安城市 | 1(48ページ) | 0 | `div.col_main` |
| 浦添市 | 2(36、14ページ) | 0 | `div.text-beginning`、`#content` |
| 弘前市 | 1(41ページ) | 9 | `#detail` |
| 福山市 | 1(47ページ) | 5 | `#mymainback_in` |
| 豊橋市 | 1(29ページ) | 13 | `#Middle` |

範囲の案の選び方も、試走で2回変えた。

- 汎用の判定にいちばん多く選ばれた要素を案にすると、遠野市ではページ全体(`#WrapperOut`)が案になった。汎用の判定は、同じ型の中でもページごとに違う要素を選んでいた(遠野市では5通り)。
- 見つかるページの数が同じなら本文の短い要素を選ぶ形にすると、安城市と豊橋市でフッター、弘前市で左の列が案になった。汎用の判定が、一部のページでフッターを本文に選んでいたため。
- 型のページの文字を比べ、多くのページに共通する文字(テンプレートの部分)を含まず、ページごとに違う文字を多く含む要素を選ぶ形にして、6サイトとも本文を含む要素が案になった。

案のうち、次の2つは人が見て決めたほうがよい見込みである。

- 浦添市の `div.text-beginning`:ページごとに違う文字の約6割しか入らない。
- 福山市の `#mymainback_in`:内側の `#main_body` の方が本文だけを含む見込み。

ページごとに違う文字には、題名、パンくず、更新日も入るので、案は本文よりやや広い要素になりやすい。
題名とパンくずは、本文の抽出の掃除で落ちる。

豊橋市には、8ページの別の作りの型が残った。
1万ページの案件では10ページ以上になり、承認に回る見込みである。

### 本処理

| サイト | 処理したページ | しっかり確認 | さっと確認 | 確認不要 |
| --- | --- | --- | --- | --- |
| 遠野市 | 97 | 96 | 0 | 1 |
| 安城市 | 48 | 46 | 1 | 1 |
| 浦添市 | 50 | 41 | 6 | 3 |
| 弘前市 | 50 | 50 | 0 | 0 |
| 福山市 | 52 | 50 | 1 | 1 |
| 豊橋市 | 42 | 42 | 0 | 0 |

遠野市の97ページの本処理は、共有ドライブへの書き込みを含めて約54秒(1ページ約0.55秒)だった。
1万ページなら約1時間半の見込みである。

ほとんどのページが「しっかり確認」になった。
自動で採用にしたルールが無いので、設計どおりの結果である。
339ページのうち、理由が1つだけのページは少なく、多くのページで次の理由が重なっていた。

| 理由 | ページ |
| --- | --- |
| 表の題名(`table.caption`) | 193 |
| 見出しの順(`html-structure.heading-order`) | 183 |
| レイアウトの表(`table.layout-table`) | 175 |
| 注記の記号(`text.note-symbol`) | 115 |
| 表の作り(`table.simple-structure`) | 109 |
| リスト(`text.list`) | 100 |

`FLOW.md` の日程の目安(しっかり確認15%)とは大きく離れている。
確認の深さを下げるには、段2で、これらのルールの候補の精度と、確認の深さの決め方を見直す必要がある。

### 共有ドライブの同期

- 遠野市の本処理で共有ドライブに書いた97ファイルは、処理の終わりから約6秒でアップロードまで終わった。書き込みにアップロードが追いついている(Drive for desktop のログに記録されたファイルの名前を数えて測った)。
- 1ページあたり3ファイル(旧ページ、台帳、候補)を書く。

ファイルの大きさは、サイトによって大きく違った。

| サイト | 候補のファイル(1ページの平均) |
| --- | --- |
| 浦添市 | 47KB |
| 遠野市 | 161KB |
| 豊橋市 | 698KB |
| 安城市 | 703KB |
| 弘前市 | 1,355KB |
| 福山市 | 1,588KB |

旧ページは、遠野市で1ページ平均47KBだった。
福山市の大きさなら、1万ページで候補のファイルだけで約16GBになる。
同期の速さよりも、共有ドライブの容量と同期の量が先に問題になる。
候補のファイルの中身(候補ごとに持つ HTML の写しなど)を減らすことを、次の段で検討する。

## 段1で決めることの答え

| 決めること | 答え |
| --- | --- |
| 取得と処理の速さ | 1万ページで、取得が約3時間半、本処理が約1時間半の見込み。ディレクターの PC で夜に回せる |
| 型の数と承認にかかる時間 | 6サイトとも、10ページ以上の型は1〜2。型の承認は案件ごとに数回で済む見込み |
| 共有ドライブの同期のしかた | 同期は書き込みに追いつく。候補のファイルの大きさを減らすまでは、1万ページの案件を共有ドライブに置けない |

## 試走で直したこと

- 取得のあとにプロセスが閉じない不具合。
- 型のまとめを、構造の重なりでまとめる形に変えた。
- 範囲の案を、型のページの文字の比べ合わせで選ぶ形に変えた。
- 構造の取り方に版を付け、取り方を変える前の承認を使わないようにした(取り方を変える前の承認が、別の型のページを引き取っていた)。
- 保存した旧ページを、取り直さずに調べ直すコマンド(`fetch --reinspect`)を足した。
