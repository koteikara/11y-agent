# LLM 提供元の評価（L2、2026-09-24）

設計書 `goal2-app/LLM_PROVIDER_SWITCH_INSTRUCTIONS.md` の 4章 L2 として、画面が実際に送る要求を集め、Gemini とさくらの AI Engine に流し直して比べた。
実装担当（Opus）が行い、評価の道具は `goal2-app/tools/llm-provider-eval.js`、人の判定用の CSV は `memory/llm-eval/` にある。

## 要点

- 文字のタスクは、さくらの gpt-oss-120b（構成 C）が機械で判定できる目安をすべて満たした。JSON は 213 件すべて1回目で妥当、分類の一致率は 91.6%、応答時間の p95 は 1.9 秒（見出しの見直しは 4.4 秒）で、1ページあたりの費用は Gemini 2.5 Flash の約3分の1だった。
- ただし C は、スキーマで任意になっている項目をほとんど返さない。感覚的な特徴の `explanation`、画像の `complex_detail` と `extracted_text`、リンクの `confidence` が一度も返らなかった。画面は `extracted_text` が空だと「画像化された文字」の候補を作らないので、C の画像のタスクでは、この候補が1件も出ない。
- 画像のタスクは、C（Qwen3-VL）も D（gemma-4）も、いまのままでは載せられない。C は数字や固有名詞を読み違える（年を 2025 や 2022 と書く、RAINBOW BRIDGE を RAINBOW BROTHERS と書く、簡体字の「实」が混ざる）。D は、システム指示を付けると画像を読まずに答える。
- Gemini 2.5 Flash（構成 A）自身も、画像の要求 3 件が 180 秒で答えを返さず、うち 2 件は再実行しても同じだった。

## 構成と条件

| 構成 | 文字 | 画像 | 費用の単価 |
|---|---|---|---|
| A | Gemini `gemini-2.5-flash`（API キー経由、温度 0） | 同じ | 入力 0.3、出力 2.5 ドル（100万トークン） |
| A2 | A と同じ設定でもう一度流したもの。A 自身の揺れの基準として足した | 同じ | 同じ |
| B | Gemini `gemini-3.5-flash`、`GEMINI_TEMPERATURE=1` | 同じ | 入力 1.65、出力 9.9 ドル（設計書 3.8 の東京の Vertex AI の単価） |
| C | さくら `gpt-oss-120b`（`reasoning_effort: low`） | `preview/Qwen3-VL-30B-A3B-Instruct` | 文字 15/75 円、画像 10/30 円 |
| D | C と同じ | `preview/gemma-4-31B-it`（画像のタスクだけ流した） | 画像 24/96 円（2026-09-24 の公式の料金表） |

- どの構成も `LLM_FALLBACK_PROVIDER=none` にした。
- 1件ずつ、1.5 秒の間をあけて流した。429 は一度も出なかった。
- 1回の呼び出しの上限は、本番の 45 秒ではなく 180 秒にした。45 秒で切ると、見出しの見直しの目安（90 秒）を測れないためである。45 秒を超えた件数は表に別に出した。
- 1分あたりの上限（`LLM_MAX_CALLS_PER_MINUTE`）は、道具の側で間をあけるので大きくした。
- 呼び出し回数は、`__setTestHooks({ fetch })` で本物の fetch を包んで数えた。「1回目で妥当」は、呼び出しが1回で妥当な JSON が返ったものである。
- 費用は、`callLlm()` が返すトークン数と上の単価からの概算である。失敗した要求はトークン数が返らないので、費用に入っていない。

## 手順

```
cd goal2-app
# 1. 要求を集める（提供元は設定しない。サーバーは道具が LLM_RECORD_DIR 付きで起動する）
node tools/llm-provider-eval.js capture --dir <作業フォルダー> --saga --pages <遠野市のページの JSON>
# 2. 流し直す（A〜D を順に。A2 は --config A2 で別に流した）
node tools/llm-provider-eval.js run --dir <作業フォルダー> --config all --gap-ms 1500
# 3. 集計する
node tools/llm-provider-eval.js report --dir <作業フォルダー> --md <表の出力先> --csv-dir ../memory/llm-eval
```

作業フォルダーには、ページの HTML、画像、要求、生の応答が入るので、リポジトリの外（scratchpad）に置き、コミットしていない。
遠野市のページの JSON は `{ id, url, title, html }` の配列である。
`--image-map` で画像の URL を差し替えられるが、今回は使っていない（上の `web.archive.org` の件）。

「1ページあたり」は、まとめた 213 件の費用を 71 ページで割ったものである。
「共有分もページごとに数えた場合」は、複数のページが同じ要求を送ったとき（ファイルのアイコンの画像など）に、そのページの数だけ数えたもので、プロセス内のキャッシュが効かない場合の目安になる。

A の JSON の妥当率が 99% を切ったのは、画像の要求 3 件が 180 秒で答えを返さなかったためである。
同じ 3 件をもう一度流すと、2 件は再び 180 秒で止まり、1 件は 9 秒で答えた。A2 でも別の1件が止まった。
本番の 45 秒の上限では、どれも `llm_request_failed` になり、画面はルールベースの案を残す。

A2 は A と 98.8% 一致した。温度 0 の Gemini 2.5 Flash は、同じ入力にほぼ同じ答えを返す。
したがって、B と C の一致率が 90% 台前半にとどまるのは揺れではなく、モデルの判断の違いである。
見出しの見直しは、A2 でも A と 76〜92% しか一致しない。自由度の高いタスクなので、一致率は参考にとどめた。

## 所見（実装担当が抜き取りを読んで気づいたこと）

人の判定の代わりではない。

7. **B（Gemini 3.5 Flash、温度 1）は、崩れや繰り返しは見られなかった。**

## 設計との差

- 佐賀市の画像が取れず、画像のタスクは遠野市の画像だけで評価した。そのため遠野市のページを約 10 件から 20 件に増やした。

- A を2回流した（A2）。一致率の目安の意味を確かめるためである。

## 次に決めること

1. **文字のタスクをさくらに移すか。** 機械の目安は満たしたが、任意の項目を返さない点（所見1）を先に直すのがよい。直し方は次の2と一緒に決める。
2. **任意の項目をどう扱うか。** 案は、(a) さくらに送るスキーマだけ、すべての項目を `required` にする（空の文字列を許す）、(b) `lib/llm-prompts.js` のスキーマ自体を変える、(c) プロンプトで「真のときは必ず書く」と強める、の3つである。(a) は Gemini に影響しない。どれも `lib/llm.js` か `lib/llm-prompts.js` の変更で、この PR ではしていない。
3. **画像のタスクをどうするか。** いまの結果では Gemini のままにする（設計書 4章 L2 の「合格しなければ Gemini のまま」）。gemma-4 を試し直すなら、openai-compatible アダプターに「システム指示を `user` の本文に入れる」設定を足してから評価をやり直す。
4. **画像の Gemini をどのモデルにするか。** A（2.5 Flash）は画像の要求で 180 秒止まることがあり、B（3.5 Flash）は止まらなかった。Vertex AI の 2.5 Flash は 2026-10-20 に廃止されるので、案 A（3.5 Flash）の判断材料にしてよい。
5. **人の判定。** CSV の判定の列をユーザーが埋め、文言の目安（「さくらが良い」と「同等」で 80% 以上）と食い違いの判定を出す。
6. **本番のタイムアウト。** 見出しの見直しは、B と C ではすべて 45 秒に収まり、A は 71 件中1件だけ超えた（55 秒）。さくらに移すなら、いまの 45 秒のままでよい。
