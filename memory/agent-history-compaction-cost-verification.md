# agent-history-compaction-cost-verification.md

## Purpose

この文書は、ユーザーの ForLLM ノート「エージェント履歴を関連度スコアで圧縮する」（2026-09-25 版。実装例と情報源が加わった改訂版）の方式で、本プロジェクトの費用と時間を減らせるかを検証した結果を記録する。

前回の検討（`memory/agent-context-relevance-compaction-research.md`、2026-09-20）は設計案と既存設計の対応づけにとどまり、一次資料も数値も確かめていなかった。
今回は、ノートが挙げる一次資料を読み、このリポジトリの会話記録と本番 LLM の実測値を使って試算した。

検証日は 2026-09-25。

## 結論

- **本番アプリ（`goal2-app`）の LLM 呼び出しには効かない。** 呼び出しは毎回独立の 1 往復で、圧縮する履歴が無い。1 ページあたりの LLM 費用は 0.12〜0.4 円（2026-09 の評価の構成 C と A）で、減らせる余地そのものが小さい。
- **開発エージェント（このリポジトリで Claude Code や Codex を動かす作業）には効く場面がある。ただし効くのは費用ではなく待ち時間である。** プロンプトキャッシュを使う前提では、選別方式は組み込みの要約より多くの原文を残すため、圧縮後の入力費用は要約より 17〜136% 高くなった（試算）。一方で、圧縮のたびに要約の生成を待つ時間（試算で約 100 秒）が、判定器の 1 秒未満に置き換わる。
- **限定判断を小型の判定器へ任せる、という隣接の使い方は、本番アプリの候補になりうる。** ただし Jev は米国でホストされ、日本語は主対象外で、選択肢名に判定が引きずられる報告がある。実案件の本文を送る前に `goal2-app/LLM_DATA_POLICY.md` の判断が要る。

採用するかどうかは、ユーザーの手元にある長い会話記録で「圧縮のたびの待ち時間」と「圧縮後の呼び出し回数」を測ってから決める。手順は末尾の「次にやること」にある。

## 一次資料で確かめたこと

サブエージェントがリポジトリを clone してコードまで読み、公式ドキュメントと論文を取得した。5 件ともアクセスできた。

### fast-jev-compaction（MIT、最新コミット e3f262a、2026-09-17）

ノートの記述はおおむねコードと一致した。食い違いと補足は次のとおり。

- **接続方法**：Claude Code のプラグイン（function hook）である。`session.compact` を横取りし、組み込みの要約の代わりに選別した元メッセージを返す。Claude Code 2.1.274 以降の早期アクセス機能で、`CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1` が要る。README 自身が「Function hooks are early access and may change between Claude Code releases」と注意している。
- **比べる相手**：「圧縮しない場合」ではなく「組み込みの要約」である。圧縮が走る時点（既定は文脈の使用率 60%）はどちらも同じで、キャッシュはどちらでも書き直しになる。
- **固定範囲**：最初のメッセージと直近 6 件（既定）。呼び出しか結果のどちらかが固定範囲に入れば、その組は判定しない。結果がまだ無い呼び出しも判定しない。
- **3 段階**：Jev に 1 組あたり 2 問（呼び出しを残すべきか、結果の全文を残すべきか）を `noul` 型で聞き、閾値 0.5 で keep、結果を先頭 300 文字に切り詰める、組ごと外す、に振り分ける。
- **失敗時**：API キーが無い、HTTP エラー、応答の形が不正、状態が上限（推定 25,000 トークン）に収まらない、のいずれでも例外にする。フックは例外を捕まえて組み込みの要約へ戻す。独自の再試行は無い。
- **削減率の下限**：フック側だけにあり、文字数で 25% 未満なら組み込みの要約へ戻す。
- **ノートとの食い違い**：README の「scored in one fast request」は、コード上は質問数に応じて複数リクエストに分けて並列に送る。「Jev's 32k request limit」は、公式ドキュメントでは状態と最長の質問 1 つの合計が 32k、1 リクエスト全体は 64k である。
- **ベンチマーク**：削減率、待ち時間、費用、精度の数値はリポジトリに無い。テストは偽の Jev を使う。

### Jev（TypeSafe の公式ドキュメント）

- ホスト型 API（`api.typesafe.ai`）で、状態と型付きの質問（Choice、Score、Noul）を送り、確率つきの答えを受け取る。文章は生成しない。
- 料金は入力 100 万トークンあたり 0.042 ドルで、出力は無料。
- 待ち時間は「Most queries complete in about 100 ms」とある。browser-use の録画では中央値 178 ms だった。
- 日本語について「English is the primary training language … Other languages, including CJK scripts, are handled but not equally well」とある。
- 「The Services are hosted in the United States」。ゼロデータ保持は enterprise 顧客だけで、日本のリージョンの記載は無い。

### そのほかの資料

- **browser-use/jev-ultrafast**：中央値 9.450 秒から 7.092 秒は `docs/performance.md` の表と一致した。Google Flights の 1 タスクを 3 組、交互に 6 回流した比較で、作者は「Three pairs are too few for a strong statistical claim (two-sided sign-test p = 0.25)」と書いている。ノートどおり、製品選定の根拠には使わない。
- **laya-mlx**：Jev ではなく、オープンウェイトの Laya を Apple MLX へ移した非公式の実装（Apache-2.0）。Apple Silicon と macOS 14 以上が要る。README の見出し値 13.42 ms と BENCHMARKS.md の 17.75 ms（同じ条件）が食い違っている。Cloud Run と Windows `.exe` で配る本プロジェクトの環境では動かない。
- **Type-Safe Is Not Error-Free（arXiv:2609.26758）**：実在し、v2 は 2026-09-23。説明文を変えず、どの選択肢名にどの説明を結び付けるかだけを入れ替えると、選択肢名を 0/1 から no/yes に変えただけで 100 件あたり 70.4 件の答えが変わり、AUC が .94 から .23 に反転した。ホスト型の Jev でも AUC が .8146 から .5806 に下がった。型エラーは全条件で 0% だった。

## 実測と試算

### 本番アプリの LLM 呼び出し

2026-09 の提供元の評価（`memory/llm-provider-eval-2026-09.md`）の値を使った。

| 構成 | 1 ページあたり（円） | 共有分もページごとに数えた場合（円） |
|---|---|---|
| A（Gemini 2.5 Flash） | 0.401 | 0.417 |
| C（さくらの gpt-oss-120b） | 0.123 | 0.126 |

呼び出しは候補の補完と画像の alt 生成だけで、会話やツールの履歴を持たない。送る項目はタスクごとに選んである（`goal2-app/lib/llm-prompts.js`）。履歴の圧縮を当てはめる場所が無く、仮に入力を半分にできても 1 ページ 0.2 円以下しか減らない。

### 会話記録への規則ベースの選別

`scripts/research/simulate-history-compaction.js` を新設した。Claude Code の会話記録（jsonl）を読み、fast-jev-compaction と同じ固定範囲と 3 段階で選別する。Jev は呼ばず、代わりに規則で判定する。

- 不可逆な操作（commit、push、PR 作成など）とエラーの結果は残す。
- 後で同じファイルを読み直したか編集した Read、検索の結果、2,000 文字を超える Bash の出力、Edit と Write の確認応答は、結果を 300 文字に切り詰める。
- 組ごと外す判定はしない（保守的にした）。

この環境には長い会話記録が無く、この検証の作業中の記録 2 本（本体とサブエージェント）で試した。トークン数は文字数からの概算である。

| 記録 | メッセージ | API 呼び出し | 全履歴の削減率 | 途中で 1 回圧縮した場合の入力費用（キャッシュ込み） | 元が取れる呼び出し回数 |
|---|---|---|---|---|---|
| サブエージェント（資料の確認） | 43 | 16 | 49.1% | +16.1% | 約 43 回 |
| 本体（この検証） | 70 | 21 | 26.4% | −3.1% | 約 8 回 |

条件は、固定を直近 6 件、圧縮の発動を推定 20,000 トークン、削減率の下限を 20% とした。削減の大半は長い Bash の出力の切り詰めだった。

選別すると、それより後ろのキャッシュがすべて無効になる。キャッシュの読みはベース単価の 0.1 倍、5 分の書き込みは 1.25 倍なので、圧縮した回は残した分を書き直す費用がかかる。削った量を R、残した量を K とすると、元を取るには、その後に約 (1.25K − 0.1(K+R)) ÷ 0.1R 回の呼び出しが要る。半分削れば約 10 回、2 割しか削れなければ約 45 回である。

### 組み込みの要約との比較（シナリオ）

fast-jev-compaction が置き換えるのは組み込みの要約なので、同じ時点で圧縮する 3 方式を比べた（`--scenario`）。前提は次のとおりで、どれも仮定の値である。

- 圧縮の時点で履歴は 120,000 トークン、以後 1 回の呼び出しごとに 2,500 トークン増える。
- 要約は 6,000 トークンを出力し、出力単価は入力の 5 倍、生成は毎秒 60 トークン。
- 選別の判定器は Jev の単価で、縮約した履歴（最大 30,000 トークン）を 4 回送る。待ち時間は 0.5 秒とした。

| 残す割合 | 圧縮後の呼び出し | 要約（相対費用） | 選別（相対費用） | 選別の増減 |
|---|---|---|---|---|
| 30% | 5 | 70,625 | 82,385 | +16.7% |
| 30% | 20 | 171,500 | 228,260 | +33.1% |
| 30% | 60 | 715,500 | 892,260 | +24.7% |
| 50% | 20 | 171,500 | 306,260 | +78.6% |
| 70% | 20 | 171,500 | 384,260 | +124.1% |

圧縮のたびの待ち時間は、要約が約 100 秒（6,000 ÷ 60）、選別が 0.5 秒である。

Jev の費用は 1 回の圧縮で相対値 1,260 程度で、どの行でも 2% に満たない。選別が高くつく原因は判定器ではなく、原文を多く残すことで以後の呼び出しの入力が増えることである。

この比較には、要約で細部が落ちたために読み直す費用と、誤った作業をやり直す費用が入っていない。選別の利点はそこにあり、ノートが「削減率だけで採用を決めない」と書いているのもこのためである。

## 本プロジェクトでの使いどころ

1. **本番アプリの履歴の圧縮**：使わない。圧縮する履歴が無い。
2. **開発エージェントの圧縮の置き換え**：待ち時間を減らす目的なら候補になる。費用は要約より増える見込みで、費用削減の手段としては採らない。早期アクセスの function hook に依存し、会話の全体（コード、差分、顧客の HTML を含みうる）を米国の Jev へ送る。導入するなら、送る範囲をユーザーが了承してからにする。
3. **限定判断の振り分け（本番アプリ）**：前回の検討の 1 番目（`memory/agent-context-relevance-compaction-research.md`）に当たる。外国語か、感覚的な表現か、見出し案が妥当か、のように答えが限られる判断を Jev のような判定器に任せると、1 回あたり数秒かかる Gemini の呼び出しを 100〜200 ms に置き換えられる可能性がある。2026-09 の評価で集めた 213 件の要求と A との一致率の枠組みで比べられ、判定器の費用は全件（入力は約 27 万トークン）でも 2 円程度の見込みである。ただし、日本語が主対象外、米国ホスト、選択肢名で答えが変わる報告があり、ラベル名と閾値を自分のデータで校正する前提になる。
4. **Claude API の context editing**：Claude API には古いツール結果を消す context editing（`clear_tool_uses_20250919`、ベータ）があり、判定器なしで同じ種類の削減ができる。開発エージェントを自前の API ループで動かす場合は、判定器より先にこれを試す。

## 次にやること

- ユーザーの手元の長い会話記録（`~/.claude/projects/<project>/*.jsonl`）でスクリプトを流し、削減率と「元が取れる呼び出し回数」を集める。圧縮後に呼び出しがそれより少ない会話が多ければ、費用目的の導入はしない。

  ```bash
  node scripts/research/simulate-history-compaction.js ~/.claude/projects/<project>/*.jsonl --keep-last 6 --trigger 60000
  node scripts/research/simulate-history-compaction.js --scenario
  ```

- 同じ記録で、組み込みの要約が何回起き、1 回あたり何秒待ったかを数える。待ち時間の合計が作業時間に対して小さければ、選別方式は入れなくてよい。
- 3 を試すなら、先に `goal2-app/LLM_DATA_POLICY.md` の条件（米国への送信、保持）をユーザーが判断する。公開済みページの本文だけを送る前提で、分類のタスク（`foreign-language`、`sensory-characteristics`）から小さく比べる。

## Limits

- 会話記録は 2 本で、どちらも 1 時間に満たない。長時間の作業での削減率は測れていない。
- トークン数は文字数からの概算で、システムプロンプトとツール定義（圧縮の影響を受けない固定部分）を含めていない。
- 選別は規則ベースで、Jev の判定の精度は測っていない。Jev の API キーは無く、呼んでいない。
- タスクの成功率、制約を守れた割合、捨てた情報の再取得の回数は、ノートが求める指標だが、この検証では測れていない。
- 要約の出力量と生成速度は仮定の値である。
