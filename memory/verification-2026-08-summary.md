# verification-2026-08-summary.md

## Purpose

この文書は、2026年8月に実施した3方式比較の検証作業について、実際に何をどこまで行ったかを記録する。

検証の設計と手順は `goal2-app/public/verification-guide.html` に定義してある。
この文書は、その設計に対して実績がどうだったかを扱う。

記録の元になったのは次の2つのスプレッドシートである。

- 移行管理シート: 5自治体×3方式の作業記録、CMS取込結果、難易度、質問と回答、顧客向け報告を保持する。
- AI移行の指摘シート: AI移行を試した作業者が気づいた点と改善要望を1件1行で保持する。

## 検証の設計

同一ページを3つの方式で作業し、所要時間と品質を比べる設計にした。

- 通常移行: ツールを使わず、これまでどおりの手順で移行する。比較の基準になる。
- AI移行: CMSで解析まで実行したソースを候補レビュー画面に入力し、修正基準を「移行ルール全体」にしてレビューし、最終HTMLをCMSへ戻す。
- miChecker移行: 入力は同じで、修正基準を「miChecker指摘対応のみ」に絞る。miChecker本体との結果一致確認を追加で行う。

対象は1自治体あたり50ページ、5自治体で最大250ページとし、3方式の延べ750件を上限の目安に置いた。
オペレーターは3グループに分け、1グループが1方式を担当する形にした。
先に作業した人の結果を後の人が見ないよう、作業順と共有範囲を分けている。

時間はツール作業とCMS作業に分けて分単位で打刻し、5分以上の中断は所要分から差し引く取り決めにした。

## 実施したこと

### 対象ページの準備とCMS取込

5自治体（安城市、浦添市、弘前市、福山市、豊橋市）の対象ページを確定し、移行管理IDを振った。
移行管理シートの各方式のシートには、安城市50ページ、浦添市50ページ、弘前市50ページ、福山市52ページ、豊橋市50ページの計252行を用意してある。

通常移行用のCMS取込は250件を実行し、全件が「新規取り込み」「完了」で終わった。
このうち5件は、取り込みは完了したものの素材の登録に失敗している。

| 移行管理ID | 失敗内容 |
| --- | --- |
| stdmig-hirosaki-001 | 画像の登録に失敗（`images/i_yotsuba.png` ほか） |
| stdmig-hirosaki-002 | 画像の登録に失敗（`images/ringo.png` ほか） |
| stdmig-fukuyama-014 | ファイルの登録に失敗（xlsx 1件） |
| stdmig-fukuyama-027 | ファイルの登録に失敗（pdf 複数） |
| stdmig-fukuyama-029 | ファイルの登録に失敗（pdf 複数） |

安城市については、対象50ページに難易度ランクを付けた。
内訳はSS 15ページ、S 15ページ、A 10ページ、B 10ページで、3方式のシートに同じ配分で入っている。
他の4自治体の難易度欄は空のままである。

### 記録の仕組みを整えた

作業時間をオペレーターが手計算しなくて済むよう、スプレッドシートにApps Scriptの作業記録パネルを組み込んだ。
ツール作業とCMS作業の開始と終了を打刻すると、対応する列に時刻と所要分が入る。
シートには導入手順とFAQも置いてあり、初回のGoogle認証で止まらないようにしてある。

miChecker結果を一覧に取り込むためのシート（`miChekcer一括調査結果CSV貼り付け`、`miChecker一覧用関数`）と、難易度調査結果の貼り付け用シートも用意した。
どちらも枠だけの状態で、データはまだ入っていない。

3方式を1行に並べて比べる `3方式比較` シートを作った。
各方式のシートのツール作業時間、CMS作業時間、合計を参照し、ステータスは中断、公開完了、公開せず完了、公開作業中、移行完了、作業中、未着手の順に判定する数式を入れてある。
ページタイトルが3方式で一致しているかを照合する列も持たせた。

## 3方式の比較はまだ成立していない

集計の枠はできているが、比較に使える状態ではない。

通常移行の計測は安城市5ページと浦添市49ページしかなく、AI移行の計測は安城市48ページしかない。
同一ページを3方式で作業した組は、安城市の一部に限られる。

浦添市の通常移行の平均7.7分は、安城市のAI移行の35.9分と同じ土俵に乗らない。
浦添市はツール作業の打刻がなくCMS作業だけで、1ページあたりの打刻間隔も1分から6分程度のものが多い。
難易度ランクも付いていないため、ページの重さを揃えた比較ができない。

安城市の通常移行の5件は16分、28分、37分、38分、190分で、190分の1件が平均を押し上げている。
母数が少なく、基準値として使える段階にない。

## AI移行で出た指摘

AI移行を試した作業者から15件の指摘が上がっている。
対象ページは遠野市（`www.city.tono.iwate.jp`）のもので、移行管理シートの5自治体とは別の試行である。
9件には証跡ファイル（`goal2_*-evidence.csv` など）が紐づいている。

内訳は、ツールへの指摘が12件、移行ルールの未確定が2件、CMS機能への要望が1件である。
効果の種別としては工数削減が9件、品質向上が6件に分類されている。

不具合として挙がったもの。

- 表が真っ黒に表示される。
- 却下ボタンが押せないのに「N件中 0件が未処理です」と表示され、出力へ進めてしまう。
- 採用ボタンが押せず、やむを得ず却下を選んだ。
- 文言修正を採用しても最終HTMLに反映されない。

候補の出し方への指摘。

- 見出しの提案が先頭の2つ程度までしか出ず、長いページでは見出しの順番が崩れる。残りはCMS側で設定し直すことになる。
- 表のキャプションがページごとに違う文言で提案され、同じシリーズの表で揃わない。
- 「データ表として維持し構造を整える」を選ぶと、表の先頭に1行追加されて後から直すことになる。
- 通常のテキストに対して見出しの提案が出ることが多く、却下してよいのか判断がつかない。
- 同じ箇所に複数の修正候補があるとき、「確認不要をまとめて採用」を先に押すと他の候補が選べなくなる。

取り込みと往復での手戻り。

- 取り込み時に改行が落ち、太字も外れるため、結局は移行元からコピーし直すことになる。
- 貼り直すと、ツールで置き換えた文字が消える。
- 画像の2枚並び、3枚並びが維持されず、すべて1枚並びで取り込まれるため並べ直しが要る。
- 写真に写り込んだ文字まで文字起こしされ、画像名ではなくHTMLパーツとして入ってしまう。
- ファイルアイコンにも画像名の修正候補が出る。
- メールリンクに件名が自動で設定されるが、通常の移行では件名を入れない。

ルールとして決めるべき点。

- 電話番号、曜日表記、全角数字といった文字の置き換えを、ツールで1件ずつ確認するのか、CMSの一括変換で行うのか。
- ページ全体が1つのHTMLとして取り込まれる場合に、どの単位でパーツへ分けるのか。

要望として、複数ページをまとめて処理すること、修正パターンを登録して呼び出すこと、「この項目ごとに表を分割してほしい」のように作業者がツールへ依頼できることが挙がっている。

## 記録運用で見つかった課題

証跡欄の書き方が揃っていない。
安城市のAI移行では50件中49件に記入があるが、移行管理IDだけのものが36件、SharePointのリンクが7件、証跡ファイル名が6件、Googleドキュメントのリンクが1件と混在している。
証跡CSVから候補件数や採用と却下の内訳を集計する設計になっているため、このままでは集計できない。

ガイドでは記録用スプレッドシートを作業記録、品質評価、miChecker一致確認の3シート構成にすると定めたが、実際に運用したのは移行管理シートに作業時間の列を足した形である。
品質評価とmiChecker一致確認は記録されていない。

浦添市のAI移行では、担当者名が作業者メモ欄に入っている。
移行担当者の列は空のままで、担当者の集計がずれる。

安城市の通常移行に、ツール作業時間が2件入っている。
通常移行はツールを使わない方式のため、打刻の押し間違いか、記録ルールの理解のずれと考えられる。

- 移行前後のmiChecker検査と「問題あり」件数の記録。比較用の `michecker-compare.html` は実装済みだが、CSVは投入されていない。

- 浦添市のAI移行とmiChecker移行。

- 難易度調査結果の貼り付けと、浦添市以降の難易度ランク付け。
