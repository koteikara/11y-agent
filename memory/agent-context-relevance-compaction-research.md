# agent-context-relevance-compaction-research.md

## Purpose

この文書は、ユーザーの Obsidian ノート「エージェント履歴を関連度スコアで圧縮する」（2026-09-18、状態は仮説）に書かれた設計案を、本プロジェクトの Goal 2 実行画面（`goal2-app/`）と構造変更1（`goal2-app/TONO_FEEDBACK_FIX_INSTRUCTIONS.md` 3章）に照らして検討した結果を記録する。

ノートの内容は X の投稿から抽出した設計仮説であり、実装（Jev など）の速度・費用・精度は一次資料で未検証である。この文書でも、本プロジェクトへの当てはめは「検討」であって、採用の決定ではない。

## Source Note

検討日は 2026-09-20。元ノートの要点は次のとおり（ユーザーが貼り付けた本文から書き起こし）。

- 長時間動くエージェントでは、履歴全体を要約し直す代わりに、ツール呼び出しや DOM 要素を「現在の目的との関連度」で評価し、不要なものを次の文脈から外す。判断に必要な結果と失敗理由は残す。
- ブラウザ操作では、各ステップで利用可能な操作と DOM 状態を絞り直す。
- 文字入力など判断が難しい操作だけ、小型 LLM へフォールバックする。
- 分岐を Choice（どれか）、Score（どの程度か）、成立する確率、という限定された判断へ分解する。
- `State → Questions → Action → Verify` の順で、実行後の新しい状態を必ず読み直す。
- 同じ状態に対する複数の判断はまとめて評価し、直列呼び出しを減らす。
- 適用先は、モデル・ツール・ブラウザ操作・人へのエスカレーションなど、選択肢が限定された分岐。
- 数学、自由文生成、不可逆な実行は決定系へ委ねず、専用コード、LLM、人間が担当する。
- 実装候補として、テキスト出力確率を使う分類系をローカル実行する `laya-mlx`（Apple MLX）、`classifier.dev`、宿検索に使った `browser-use/jev-ultrafast` が挙がっている。いずれも比較条件が無く未検証。
- 導入時は精度低下、重要履歴の欠落、評価コストを測定する、とノート自身が注意している。

## 本プロジェクトの現状（2026-09-20、main = PR #135・#137 マージ後）

LLM（Gemini 2.5 Flash）の使い方:

- 呼び出しは候補の補完（`/api/llm/enrich`）と画像の alt 生成（`/api/llm/image-alt`）だけである。
- 補完は 1 要求あたり最大 50 件の候補で、各候補が持たせるのはタスクごとに選んだ数個の項目（本文、近くの文、直前の見出し、表の HTML、ページタイトルなど。`goal2-app/lib/llm-prompts.js`）である。
- 会話やツール呼び出しの履歴は持たない。毎回独立の 1 往復である。

このアプリで「履歴」に当たるもの:

- 決定ログ（`state.decisions`）。世代を重ねるほど増え、取り下げ（`withdrawn`）の行が多い（佐賀市の実ページ 51 件の画面経路で 290 行）。リプレイは候補ごとに最新の決定だけを当てる（`latestDecisions()`）ので、処理上は最新だけを見る形になっている。
- 案件の中でページをまたいで積み上がる作業者の判断（同じ種類の候補の却下、同じ言い換えの編集、要確認の理由）。どこにも活かされていない。

## ノートの設計案と本プロジェクトの対応

ノートの設計案の大半は、本プロジェクトが別の経緯で採っている形と一致する。

| ノートの設計案 | 本プロジェクトの対応 |
| --- | --- |
| `State → Questions → Action → Verify`。実行後の状態を読み直す | 構造変更1 S3。決定 → リプレイ → 作業中 HTML から候補を作り直す → 照合（3.5・3.6） |
| 同じ状態への複数の判断をまとめて評価し、直列呼び出しを減らす | 一括採用を 1 世代にまとめて再導出 1 回（3.14）。AI 補完を 50 件ずつ 1 往復 |
| Choice／Score／成立確率に判断を分解する | 候補の `confidence`、`requires_human_review`、KB の `processing_class`（mechanical／hybrid／escalation） |
| 自由文生成と不可逆な実行は決定系に委ねない | AI は下書き（`ai_draft`）まで。要確認は人。CMS 登録は手作業 |
| 判断に必要な結果と失敗理由を残す | S4 の証跡で `orphaned`（当たらなかった）と `withdrawn`（差し替わった）を区別する（3.11） |
| DOM 状態を各ステップで絞り直す | Goal 3 の本文抽出（`scoreCandidate()`）、Content-Only Scope Boundary、補完に送る項目の選別 |

「履歴を関連度で圧縮する」という中心の主張そのものは、いまの LLM 呼び出しには当てはまる場所が無い。文脈はもともと小さく選別されている。

## Implications for This Project

発展の余地を、価値の高い順に挙げる。

1. **限定判断を小型分類器で先に振り分ける**。いまは正規表現か Gemini に頼っている判断のうち、出力が限られるものが対象になる。見出し提案の妥当性（遠野市の指摘 6）、分数を日付と誤検出する `text.partial-date`（issue #136）、レイアウト表かデータ表か、リンク文言の良し悪し、など。ラベルは 2026 年 8 月の検証の採用・却下記録と、佐賀市 51 件の gold から作れる。Gemini への送信が減るので `goal2-app/LLM_DATA_POLICY.md` の懸念とも相性がよい。ノートが挙げる `laya-mlx` や `classifier.dev` はこの用途の候補だが、未検証。
2. **案件内の判断履歴を関連度で絞って補完に渡す**。ノートの「ツール呼び出し単位で関連度を付け、低いものを外す」を、過去の決定（同じルール、同じ文言、同じ構造）に当てはめる。同じシリーズの表でキャプションが揃わない、同じ却下を繰り返す、といった問題に効く。課題候補 B01（案件別の上書き、`memory/project-issue-candidates.md`）と重なる。着手は S5（GOAL1 のループ化）の後。
3. **再導出を影響範囲の部分木に絞る**。ノートの「DOM 状態を各ステップで絞り直す」に当たる。3.14 の上限 300 ミリ秒に対して現状は最大 109 ミリ秒（PR #135 の計測）なので、超えるまで不要。設計書 3.5 に対策として書いてある。
4. **CMS 登録のブラウザ操作の自動化**（browser-use 系）。取込ツールへ戻す工程は手作業だが、CMS への登録は不可逆で、ノート自身の規則（不可逆な実行は人か専用コード）に触れる。いまは対象外。

前提と注意:

- 1 に着手するなら、ラベルの元になる証跡（採用・却下・編集後の文言）を案件横断で集める仕組みが先に要る。S4 の証跡設計に「分類器の学習に使える列」を意識して入れておくと安上がりである。
- 精度の比較には、本プロジェクトの既存の枠組み（実ページ 51 件の同一性比較、回帰テスト 198 件、`goal2-app/agents-cli/` のローカル評価）をそのまま使える。ノートが注意している精度低下・重要履歴の欠落・評価コストは、この枠組みで測る。
- 履歴を Gemini に送るなら、`goal2-app/LLM_DATA_POLICY.md` の条件（顧客データの送信可否、保持）を先に満たす。圧縮は送る量を減らす方向なので方針とは矛盾しない。
